# FCP vs LCP —— 面试版

> 面试官问："FCP 和 LCP 分别是什么？有什么区别？怎么优化？"



# 八、面试现场：标准回答模板

> **面试官**："说一下 FCP 和 LCP 的区别？"

> **你**：
> FCP 是首次内容绘制，指浏览器把第一个 DOM 内容渲染到屏幕的时间，回答的是"白屏多久结束"。LCP 是最大内容绘制，是视口内最大的可见元素完成渲染的时间，回答的是"主要内容加载完了没"。
>
> 关键区别有 4 点：
> 1. FCP 出现任意文字就算，LCP 追踪的是最大元素
> 2. FCP 一次性确定，LCP 会回溯更新（新的更大元素出现就更新时间）
> 3. LCP 是 Core Web Vitals 三大核心指标之一，FCP 不是
> 4. FCP ≤ 1.8s 算好，LCP ≤ 2.5s 算好
>
> 优化上，FCP 主要靠减阻塞（主要检查服务端，优化重点服务端TTFB高或HTML传输慢，内联关键 CSS、defer JS、SSR），LCP 主要靠加速最大元素的加载（preload 大图、CDN、避免 JS 动态插入 LCP 元素）。
>
> 排查问题时：FCP 和 LCP 都慢 → 查 TTFB/服务端；FCP 快 LCP 慢 → 查大图/JS 动态渲染。


TTFB：首字节时间，浏览器发出请求到服务器返回第一个字节时间，主要是服务器做优化，比如CDN/边缘缓存缩短网络距离，服务端缓存命中热点数据，数据库和接口优化
---

# 一、一句话区分

| 指标 | 一句话 |
|------|--------|
| **FCP**（First Contentful Paint） | 用户看到**第一个像素**的时刻（"白屏结束了"） |
| **LCP**（Largest Contentful Paint） | 用户看到**主要内容**的时刻（"页面有用了"） |

> FCP 回答"页面有反应了吗？" → LCP 回答"页面能用了吗？"

---

# 二、定义（面试标准回答）

## FCP —— 首次内容绘制

**浏览器首次将任何 DOM 内容（文字、图片、SVG、非白色 canvas）渲染到屏幕的时间点。**

```
用户输入 URL → DNS → TCP → TLS → 请求 HTML → 解析 HTML
                                                    ↓
                                              FCP（第一个文字/图片出现）
```

- 从 `navigationStart` 开始计时
- 内容包括：文本、图片（含背景图）、SVG、非白色 `<canvas>`
- **不包括**：iframe 内容、加载中的字体文字（不可见文字不算）

## LCP —— 最大内容绘制

**视口内最大可见元素（文本块/图片/视频/背景图）完成渲染的时间点。**

```
FCP → 更大的图加载完 → LCP
         ↑
    浏览器持续追踪哪个元素最大，
    每次出现更大元素就更新 LCP 时间
```

- 浏览器会持续追踪，直到用户首次交互（点击、滚动、键盘输入）
- 最终取**最大的那个元素**完成渲染的时间
- 候选元素：`<img>`、`<svg>` 内的 `<image>`、`<video>` 的封面、带 `url()` 背景图的元素、文本块级元素

# 三、核心区别（面试重点）

| 维度 | FCP | LCP |
|------|-----|-----|
| **含义** | 第一个内容出现 | 最大/主要内容出现 |
| **回答什么问题** | 白屏多久？ | 主要内容多久出来？ |
| **衡量什么** | 感知的"有反应了" | 感知的"加载完了" |
| **数据来源** | 任意内容（文字也算） | 视口内**最大**可见元素 |
| **是否回溯更新** | 不更新，一次性 | 会更新（更大元素出现时） |
| **停止时机** | 第一个内容渲染完毕 | 用户交互 或 最大元素稳定 |
| **Core Web Vitals** | 不是 | ✅ 是（三大核心指标之一） |
| **好阈值** | ≤ 1.8s | ≤ 2.5s |

# 四、LCP 的 4 种候选元素

面试官常追问："LCP 考虑哪些元素？"

```javascript
// 浏览器按以下优先级找 LCP 候选：
// 1. <img>
// 2. <svg> 内的 <image>
// 3. <video> 的 poster 属性
// 4. 带 url() 背景图的元素
// 5. 包含文本的块级元素（p, h1-h6, div 含大量文本）
```

关键规则：
- 只算**视口内**可见部分，超出一屏的不算
- 文本块按"包含所有文本的最小矩形"算
- 如果有图片和文本差不多大，图片优先

# 五、为什么 FCP 快但 LCP 慢？

面试常见场景分析题：

```
"我的页面 FCP 1.2s，但 LCP 3.8s，为什么？"
```

**典型原因：**

```
FCP 很快（1.2s） ← 首屏有个小标题文字，也算 FCP
     ↓
LCP 很慢（3.8s） ← 但 Hero 大图要等 JS 执行完才插入 DOM
```

常见情况：
1. **LCP 元素是 JS 动态插入的图片** → 要等 JS bundle 下载+执行+渲染
2. **LCP 是 `<img>` 但 src 由 JS 设置**（如 React 的 `src={url}`） → 浏览器无法预扫描
3. **LCP 元素渲染后又被新元素替换**（如轮播图、骨架屏→真实内容）
4. **背景图在 CSS 中声明** → 浏览器构建 CSSOM 后才开始加载

# 六、优化策略（面试必问）

## FCP 优化（目标 ≤ 1.8s）

| 策略 | 原理 |
|------|------|
| **精简 HTML** | 减少 DOM 大小，加速解析 |
| **关键 CSS 内联** | `<style>` 写在 HTML 中，不等外部 CSS |
| **移除阻塞渲染的 JS** | `<script defer>` 或 `<script async>` |
| **服务端渲染 / 预渲染** | 直接给 HTML，不等 JS 执行 |
| **TTFB 优化** | CDN 就近、服务端缓存、减少重定向 |
| **字体 font-display: swap** | 文字不因等待字体而不可见 |

## LCP 优化（目标 ≤ 2.5s）

| 策略 | 原理 |
|------|------|
| **preload LCP 图片** | `<link rel="preload" as="image">`，不让图片排队 |
| **LCP 元素用 `<img>` 不用背景图** | `<img>` 可被预扫描器提前发现，背景图要等 CSSOM |
| **图片压缩 + 现代格式** | WebP/AVIF + srcset 响应式图片 |
| **LCP 元素不要 lazy-load** | `loading="lazy"` 对 LCP 元素是反向优化 |
| **避免 JS 插入 LCP** | SSR/SSG 直接在 HTML 中输出 LCP 元素 |
| **CDN / 优化 TTFB** | 和 FCP 一样，源头要快 |
| **服务端渲染优先** | HTML 直接包含内容，不等 JS hydration |

# 七、FCP + LCP 同时慢 vs 单项慢

面试官追问："怎么根据指标判断问题出在哪？"

```
FCP 慢 + LCP 慢 → 源头问题（TTFB / 网络 / 服务端）
FCP 快 + LCP 慢 → 资源加载问题（大图 / JS 阻塞 / 动态插入）
FCP 慢 + LCP 快 → 罕见，通常是渲染阻塞 CSS 导致
```

# 九、WebGIS 场景下的 LCP

面试被问到项目经验时可以接：

```
我们气象 WebGIS 的 LCP 是 Cesium Viewer 的首帧渲染，
LCP 往往在 3-5s 左右，因为：

1. Cesium.js 本身 20MB+，是最大的 LCP 候选元素（canvas）
2. 地形数据 + 影像瓦片要等 Cesium 初始化后才请求
3. 10万站点 Primitive 批量渲染在首帧完成

优化手段：
- preload Cesium.js，确保最早开始下载
- Cesium Ion 的默认地球替换为静态底图（去掉动态星空背景）
- requestRenderMode 控制渲染频率，首屏加载时不浪费 GPU
- 骨架屏覆盖 canvas 区域，用户感知更好
```

# 十、三个核心 Web Vitals 关系图

```
         ┌──────────────────────┐
         │     Web Vitals       │
         ├──────────┬───────────┤
         │   LCP    │    CLS    │    INP
         │ 加载体验  │  视觉稳定  │   交互响应
         │ ≤ 2.5s   │  ≤ 0.1    │   ≤ 200ms
         └──────────┴───────────┘
              ▲
         FCP 是 LCP 的"前奏"
         (FCP ≤ 1.8s → 给 LCP 争取时间)
```

# 速记卡

```
FCP = 白屏结束 = 第一个像素 ≤ 1.8s
LCP = 内容可见 = 最大元素完成 ≤ 2.5s

都慢 → 查服务端/TTFB
FCP快LCP慢 → 查大图/动态插入
优化FCP → 去阻塞（内联 CSS、defer JS）
优化LCP → 加速主角（preload 大图、SSR 直出）
```
