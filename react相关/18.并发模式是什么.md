# React 18 并发模式（Concurrent Mode）


## 八、面试话术

### 简洁版（1 分钟）

> React 18 的并发模式核心解决的问题是：**大量渲染任务阻塞主线程，导致用户交互卡顿**。
>
> 之前 React 的渲染是同步的，一旦开始就不能中断。如果渲染一个大列表需要 200ms，这期间用户输入、点击都没有响应。
>
> 并发模式的核心是**时间切片 + 优先级调度**：把渲染任务切成 5ms 的小片段，每个片段之间检查有没有更紧急的任务。用户输入是紧急更新，立即执行；列表渲染是过渡更新，可以被中断和恢复。
>
> 开发者通过 `useTransition` 和 `useDeferredValue` 告诉 React 哪些更新可以延迟，React 自动调度执行顺序。底层依赖的是 Fiber 架构——每个组件是一个可暂停的工作单元，处理完一个检查一次，所以能做到中断和恢复。

### 结合项目版

> 这个在地图项目里其实很有应用场景。比如用户在搜索框输入地名的同时，地图需要过滤和渲染大量 POI 点。如果是同步渲染，输入框会卡；用 `startTransition` 把 POI 渲染标记为低优先级，输入框保持流畅，POI 列表延迟更新，用户体验好很多。


## 一、一句话说清本质

```
React 18 之前：渲染是同步的，一旦开始就不能中断
React 18 之后：渲染是可中断的，React 能决定先渲染什么、后渲染什么

本质：把渲染工作从"单线程阻塞"变成"可调度、可中断、可恢复"
```

```
React 17（同步模式）：

  你在餐厅当服务员

  你必须把 20 道菜全部上完，才能去服务下一桌

关键词：可中断、可插队、有优先级
```

## 三、之前为什么会卡？（同步渲染的问题）

```javascript
// 假设有一个大列表，用户在搜索框输入

function App() {
  const [input, setInput] = useState('')
  const [list, setList] = useState([])

  const handleChange = (e) => {
    setInput(e.target.value)        // 高优先级：输入框要立即响应
    setList(filterHugeList(e.target.value))  // 低优先级：列表可以慢点
  }

  return (
    <>
      <input value={input} onChange={handleChange} />
      <HugeList data={list} />  {/* 10000 条数据 */}
    </>
  )
}
```

```
React 17 的问题：

  用户输入 "a"
    → setInput('a')    ← 要更新输入框
    → setList(...)     ← 要过滤并渲染 10000 条数据
    → 两个更新合并成一次同步渲染
    → 渲染 10000 条数据需要 200ms
    → 这 200ms 内输入框卡住了，用户打字没反应

  时间线：
  ┌──────────────────────────────────────────────┐
  │  输入 "a" → [====== 渲染 10000 条 ======] → 显示 │
  │              ↑ 这段时间主线程被占满，输入框卡死   │
  └──────────────────────────────────────────────┘
```

## 四、React 18 并发模式怎么解决？

### 核心机制：时间切片（Time Slicing）

```
React 18 把一个大的渲染任务切成很多小片段（5ms 一片）
每个片段之间检查：有没有更高优先级的任务要插队？

时间线：
┌───────────────────────────────────────────────────────────┐
│                                                             │
│  输入 "a"                                                   │
│  → [渲染片段1][检查] [渲染片段2][检查] [渲染片段3][检查]...    │
│                 ↑                                           │
│           "有用户输入！暂停当前渲染，先更新输入框"              │
│           → 更新输入框（用户立即看到 "a"）                    │
│           → 恢复之前的列表渲染                                │
│                                                             │
└───────────────────────────────────────────────────────────┘

用户感受：输入框始终流畅，列表稍后更新，但完全不卡
```

### 优先级调度

```
React 18 内部给不同更新分了优先级：

  紧急更新（Urgent）          → 输入、点击、按键
    用户直接触发的交互，必须立即响应

  过渡更新（Transition）      → 搜索结果、列表过滤、页面切换
    可以稍微延迟，不影响用户体验

  React 的调度器会：
    1. 紧急更新 → 立即执行，不可中断
    2. 过渡更新 → 可以被紧急更新打断，稍后恢复
```

## 五、开发者怎么用？（三个核心 API）

### 1️⃣ `useTransition` —— 标记低优先级更新

```javascript
import { useState, useTransition } from 'react'

function App() {
  const [input, setInput] = useState('')
  const [list, setList] = useState([])
  const [isPending, startTransition] = useTransition()

  const handleChange = (e) => {
    // ✅ 高优先级：输入框立即更新
    setInput(e.target.value)

    // ✅ 低优先级：列表渲染可以被中断
    startTransition(() => {
      setList(filterHugeList(e.target.value))
    })
  }

  return (
    <>
      <input value={input} onChange={handleChange} />
      {isPending && <span>加载中...</span>}
      <HugeList data={list} />
    </>
  )
}
```

```
效果：
  用户快速输入 "abc"
  
  React 17：输入框卡顿，等列表渲染完才能看到 "abc"
  React 18：输入框立即显示 "abc"，列表稍后更新

  而且如果用户连续输入 "a" "ab" "abc"
  React 会自动丢弃 "a" 和 "ab" 的列表渲染（反正已经过时了）
  只渲染 "abc" 对应的列表 → 减少无效渲染
```

### 2️⃣ `useDeferredValue` —— 延迟一个值的更新

```javascript
import { useState, useDeferredValue } from 'react'

function App() {
  const [input, setInput] = useState('')
  // input 立即更新，deferredInput 延迟更新
  const deferredInput = useDeferredValue(input)

  return (
    <>
      <input 
        value={input} 
        onChange={e => setInput(e.target.value)} 
      />
      {/* 用延迟值渲染大列表，不阻塞输入 */}
      <HugeList filter={deferredInput} />
    </>
  )
}
```

```
useTransition vs useDeferredValue 区别：

  useTransition  → 你能控制 setState 的调用
                   "我主动告诉 React 这个更新不急"
                 
  useDeferredValue → 你控制不了 setState（比如来自父组件的 props）
                     "我告诉 React 这个值可以用旧的先顶着"
```

### 3️⃣ `<Suspense>` —— 异步内容的优雅降级

```javascript
import { Suspense, lazy } from 'react'

const HeavyComponent = lazy(() => import('./HeavyComponent'))

function App() {
  return (
    <Suspense fallback={<Loading />}>
      <HeavyComponent />
    </Suspense>
  )
}
```

```
React 18 的 Suspense 配合并发模式：

  1. HeavyComponent 还在加载 → 先显示 <Loading />
  2. 加载完成 → 切换到真实内容
  3. 切换过程可以被更高优先级的更新打断
  
  配合 startTransition 使用：
  路由切换时用 Suspense 包裹新页面
  → 旧页面可以继续显示，直到新页面准备好
  → 不会出现白屏
```

## 六、底层是怎么实现的？（Fiber 架构）

```
并发模式能实现的根基 = Fiber 架构（React 16 引入）

React 15（Stack Reconciler）：
  组件树递归比较，一条路走到底，不能停

React 16+（Fiber Reconciler）：
  把组件树拆成一个个 Fiber 节点（链表结构）
  每个 Fiber 节点 = 一个工作单元
  处理完一个节点后可以暂停，检查有没有更紧急的事
```

```
Fiber 工作流程：

  组件树：      App
              /     \
          Header    Content
                   /    \
                List    Detail

  Fiber 链表：
  App → Header → Content → List → Detail
   ↑                                  │
   └──────────────────────────────────┘

  渲染过程：
  处理 App ✅ → 检查中断 → 处理 Header ✅ → 检查中断 
  → 处理 Content ✅ → 检查中断（⚠️ 有用户输入！）
  → 暂停！先处理用户输入
  → 输入处理完 → 恢复 → 处理 List ✅ → 处理 Detail ✅

  每个 Fiber 节点记录了：
  - 自己的状态
  - 做到哪一步了
  - 下一个要处理谁
  所以暂停后能恢复
```

## 七、并发模式 vs 异步渲染——别搞混

```
常见误区：并发 ≠ 多线程

  ❌ "React 18 用多线程渲染"  → 错！JS 还是单线程
  ✅ "React 18 把渲染任务切片，在单线程上交替执行"

类比：
  多线程 = 餐厅请了 3 个服务员同时干活
  并发   = 还是 1 个服务员，但他会合理安排先后顺序
           紧急的先做，不紧急的可以等一等
```
