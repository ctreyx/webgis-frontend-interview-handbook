# React 的 Lane 模型是什么？为什么要用 Lane 替代之前的 expirationTime？

# 一、Lane 模型

expirationTime 是标量，Lane 是位掩码，位运算天然支持集合操作

为什么要替换 expirationTime？
expirationTime 本质上是一个数字时间戳，用来表示任务的优先级和过期时间。但它有一个根本性的缺陷——

expirationTime 的问题：优先级是单一数字，无法表达"批次"概念

任务 A: expirationTime = 100 （高优先级）
任务 B: expirationTime = 200 （低优先级）
任务 C: expirationTime = 150 （中优先级）

问题1：我想同时处理 A 和 C，跳过 B —— 做不到！
数字无法表达"这两个任务是同一批次"

问题2：IO 任务 vs CPU 任务，同一 expirationTime 无法区分
它们的优先级语义完全不同，但都用一个数字表示

问题3：判断任务是否在某个优先级范围，需要数值比较
O(n) 遍历，性能差

# Lane 一共有多少个？

`TotalLanes = 31`，源码里写死的常量。

其中 TransitionLanes 是专门给 `useTransition` 和 `startTransition` 准备的 16 条独立车道，这些车道可以被打断，也可以并行处理。
为什么 Transition 要独占 16 条？因为应用里可能同时有多个并发的 startTransition，每个要独立调度互不干扰，16 条够用了。
位置 Lane 名称 数量

bit 1 SyncLane 1条 ← 最高优先级
bit 2 InputContinuousHydrationLane 1条

bit 4 DefaultHydrationLane 1条
bit 5 DefaultLane 1条
bit 6 TransitionHydrationLane 1条

bit 23~28 RetryLanes 5条 ← Suspense 重试

合计 31条

# 二、Lane 在什么阶段产生，什么阶段使用？

用户操作 / 代码调用 setState
↓
requestUpdateLane(fiber) ← ★ Lane 在这里产生
↓
根据当前上下文判断：

- 在合成事件回调里？ → 看事件类型
- 在 startTransition？ → TransitionLane
- 在 setTimeout？ → DefaultLane
- 普通同步调用？ → SyncLane
  ↓
  update.lane = 计算出的Lane ← 挂到 update 对象上
  ↓
  root.pendingLanes |= lane ← OR 进根节点的待处理集合

React 内部实际上有三套优先级体系协同工作：Lane Priority 是内部对更新紧迫程度的表达，Event Priority 负责把用户交互映射到对应的 Lane，Scheduler Priority 则决定任务最终怎么被调度执行。
// 事件类型 → Lane 的映射
click / keydown / input → DiscreteEventPriority → SyncLane
scroll / mousemove → ContinuousEventPriority → InputContinuousLane
startTransition 内部 → TransitionLane（1~16 轮转分配）
setTimeout / Promise → DefaultEventPriority → DefaultLane
requestIdleCallback → IdleEventPriority → IdleLane

# ④ 饥饿处理：Lane 过期强制升优先级

优先级系统中存在"饥饿"问题，即低优先级任务因为高优先级任务不断插入而永远得不到执行；React 会追踪每个 Lane 已等待的时长，如果某个 Lane 在 `pendingLanes` 中停留太久就会"过期"，React 会自动将其合并到下一次 SyncLane 的渲染中，强制执行，保证 UI 最终一致。
