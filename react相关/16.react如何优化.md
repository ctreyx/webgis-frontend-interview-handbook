# React Bailout 机制：源码原理 + 真实项目优化




很多人做 React 性能优化的第一反应是"加 memo"，但读过源码你就会知道——memo 不是免费的。

真实项目里要触发 bailout，本质是创造几个条件：props 引用稳定、state 没有变化、context 没变化、childLanes 不包含当前 renderLanes。

所以常见手段是 React.memo 建立组件边界，useMemo 稳定对象和数组，useCallback 稳定函数引用，让 memo 子组件的浅比较能通过。

但我不会无脑加这些东西，因为它们本身也有成本。

useCallback 并没有阻止函数创建——JS 引擎执行到那一行就会创建新函数，useCallback 只是创建了又扔掉、返回旧的引用。每次渲染你还额外付出了 deps 数组创建和逐项 Object.is 比较的成本。如果子组件连 React.memo 都没包，这个引用稳不稳定根本没人检查——你付出了成本。

React.memo 也不是免费的——它每次都要做 props 浅比较。如果 props 里有未稳定化的对象或函数，浅比较每次都失败，组件每次都照常渲染——你白白多付了一次比较的成本，比不加还慢。

而且每个 Hook 调用都会在 fiber 的 memoizedState 链表上增加一个节点，缓存值和 deps 常驻内存，GC 回收不了。一个组件加 10 个 memo，乘以列表里 1000 个实例，就是 10000 个多余的链表节点。

所以我的优化原则是：先调结构（state 下沉、组件提升），让 bailout 自然生效，零成本；只有当结构动不了、子组件渲染确实很重时，才精准加 memo——知道它有成本，才知道什么时候值得付这个成本。这是读过源码和没读过源码的人做优化的本质区别。


并且据我了解 react 19有个  React Compiler 自动优化策略。



## 一、先搞清楚 Bailout 是什么

**Bailout 的意思是"提前退出"——React 在 Reconciliation 阶段判断这个组件没有变化，直接跳过它和它的整棵子树，不做 diff、不做渲染。**

大部分 React 开发者知道 `React.memo`、`useMemo`、`useCallback`，但这些只是**手动触发 bailout 的 API**。React 内部其实有**自动 bailout 机制**，很多人不知道。

---

## 二、Bailout 的触发条件（源码层面）

React 源码中 `beginWork` 函数里，进入组件处理之前会做一次检查，四个条件**全部满足**才会 bailout：

```
条件 1：oldProps === newProps（引用相等，不是深比较）
条件 2：context 没有变化
条件 3：fiber.type 没有变化（组件本身没被替换）
条件 4：没有 pending 的更新（lanes 检查）
```

**四个全部满足 → bailout → 跳过这个组件和整棵子树**

关键理解：**条件 1 是引用比较，不是值比较。** 这意味着即使 props 的内容完全相同，只要引用变了（每次父组件渲染都创建新对象），bailout 就不会触发。

## 三、为什么大部分人不知道 Bailout 在生效

```jsx
// 场景：App 的 state 变了，Child 会不会重新渲染？

function App() {
  const [count, setCount] = useState(0)
  return (
    <div>
      <p>{count}</p>
      <Child />          {/* ← 这里 */}
    </div>
  )
}

function Child() {
  console.log('Child rendered')
  return <div>我是子组件</div>
}
```

**答案：Child 会重新渲染。**

为什么？因为 `<Child />` 本质上是 `React.createElement(Child, null)`，每次 App 渲染都会创建一个**新的 ReactElement 对象**，`newProps` 是一个新的 `{}`，引用和 `oldProps` 不同 → 条件 1 不满足 → bailout 失败。

**这就是为什么大家说"父组件更新，子组件一定跟着更新"——不是因为没有 bailout 机制，而是默认写法下条件 1 几乎永远不满足。**

### 手法 1：组件提升（Component Hoisting）——零成本，效果最好 ⭐⭐⭐⭐⭐

**原理：把不依赖父组件 state 的子组件，提到父组件外面去。**

```jsx
// ❌ 反模式：Child 每次都跟着 App 重新渲染
function App() {
  const [count, setCount] = useState(0)
  return (
    <div>
      <p>{count}</p>
      <ExpensiveChild />   {/* 每次创建新的 ReactElement */}
    </div>
  )
}

// ✅ 优化：把 ExpensiveChild 提升到外层
function Wrapper() {
  return (
    <App>
      <ExpensiveChild />   {/* 在 Wrapper 层创建，引用不变 */}
    </App>
  )
}

function App({ children }) {
  const [count, setCount] = useState(0)
  return (
    <div>
      <p>{count}</p>
      {children}            {/* children 的引用没变 → bailout！ */}
    </div>
  )
}
```

**为什么有效：** `children` 是在 `Wrapper` 里创建的 ReactElement，`Wrapper` 没有 state 变化所以不会重新渲染，传给 `App` 的 `children` 引用始终不变 → `oldProps.children === newProps.children` → bailout 触发 → `ExpensiveChild` 整棵子树被跳过。

**真实场景：** 我在项目里遇到过一个列表页，顶部有实时刷新的计数器，每秒更新一次。下面是一个复杂的数据表格组件。计数器每次更新都导致表格重新渲染，页面卡顿。我不是加 `React.memo`，而是把表格组件通过 `children` 传入——**零 API 成本，bailout 自动生效。**

---

### 手法 2：State 下沉（State Colocation）——把 state 移到真正需要它的组件里 ⭐⭐⭐⭐⭐

```jsx
// ❌ 反模式：input 的 state 放在顶层，整棵树跟着抖
function Page() {
  const [keyword, setKeyword] = useState('')
  return (
    <div>
      <SearchInput value={keyword} onChange={setKeyword} />
      <ExpensiveList />        {/* 每次输入都重新渲染 */}
      <ExpensiveChart />       {/* 每次输入都重新渲染 */}
    </div>
  )
}

// ✅ 优化：把 state 下沉到 SearchInput 内部
function Page() {
  return (
    <div>
      <SearchInput />          {/* state 在内部管理 */}
      <ExpensiveList />        {/* 不再被触发 → bailout */}
      <ExpensiveChart />       {/* 不再被触发 → bailout */}
    </div>
  )
}

function SearchInput() {
  const [keyword, setKeyword] = useState('')  // state 在这里
  return <input value={keyword} onChange={e => setKeyword(e.target.value)} />
}
```

**为什么有效：** `Page` 不再有 state 变化，所以 `Page` 不会重新渲染，`ExpensiveList` 和 `ExpensiveChart` 的 props 引用不变 → bailout 触发。

**真实场景：** 搜索框 + 复杂仪表盘的组合页面。用户每输入一个字符，仪表盘里几十个图表全部闪烁重绘——把搜索的 state 从页面级下沉到搜索框组件内部，图表立刻不抖了。

### 手法 3：EagerState 优化——同值更新自动 bailout ⭐⭐⭐⭐

**这是 React 源码里一个很少人知道的优化：**

```jsx
function Counter() {
  const [count, setCount] = useState(0)
  
  return (
    <button onClick={() => setCount(0)}>  {/* 设置和当前一样的值 */}
      {count}
    </button>
  )
}
```

**点击后会重新渲染吗？不会。**

React 内部在 `dispatchSetState` 里有一个 **eagerState 优化**：如果新值和旧值通过 `Object.is` 比较相等，React 会直接跳过这次更新，不进入调度器，不触发渲染。

```
源码逻辑：
dispatchSetState → 
  计算新值 →
  Object.is(newState, currentState) === true →
  直接 return，不触发更新 →
  组件不会重新执行
```

**真实场景中的坑：**

```jsx
// ❌ 这个不会触发 eagerState 优化
const [user, setUser] = useState({ name: 'Tom' })
setUser({ name: 'Tom' })  // 新对象，引用不同，Object.is 返回 false

// ✅ 这个会触发
const [name, setName] = useState('Tom')
setName('Tom')  // 相同的原始值，Object.is 返回 true → 跳过更新
```

**启示：state 尽量用原始值（string / number / boolean），而不是对象。** 不只是为了"代码简洁"，而是原始值能触发 eagerState 优化，对象不行。

### 手法 4：稳定引用——让 Bailout 条件 1 成立 ⭐⭐⭐⭐

```jsx
// ❌ 每次渲染都创建新对象和新函数，子组件 bailout 失败
function Parent() {
  const [count, setCount] = useState(0)
  
  const style = { color: 'red' }                    // 新对象
  const handleClick = () => console.log('click')     // 新函数
  
  return <Child style={style} onClick={handleClick} />
}

// ✅ 稳定化引用
function Parent() {
  const [count, setCount] = useState(0)
  
  const style = useMemo(() => ({ color: 'red' }), [])
  const handleClick = useCallback(() => console.log('click'), [])
  
  return <Child style={style} onClick={handleClick} />
}

const Child = React.memo(function Child({ style, onClick }) {
  // ...
})
```

**注意：`useMemo` / `useCallback` 单独用是不够的，必须配合 `React.memo` 才有意义。** 因为 bailout 条件 1 要求 `oldProps === newProps`（整个 props 对象引用相等），没有 `React.memo` 的话，父组件每次渲染都创建新的 props 对象，里面的字段引用稳不稳定根本不检查。

```
没有 React.memo：
  → 父组件渲染 → 创建新的 props 对象 → oldProps !== newProps → bailout 失败
  → useMemo/useCallback 白做了

有 React.memo：
  → 父组件渲染 → React.memo 做 props 浅比较
  → 每个字段的引用都没变 → 浅比较通过 → bailout 触发
```

**这就是为什么我说"大部分人用 useMemo useCallback 是盲目的"——不理解 bailout 的触发条件，就不知道什么时候该加、什么时候加了没用。**

### 手法 5：key 稳定——防止 bailout 被 key 变化破坏 ⭐⭐⭐

```jsx
// ❌ key 用 index，列表增删时组件被销毁重建，bailout 全部失效
{items.map((item, index) => (
  <ExpensiveItem key={index} data={item} />
))}

// ✅ key 用稳定的唯一标识
{items.map(item => (
  <ExpensiveItem key={item.id} data={item} />
))}
```

**为什么：** bailout 条件 3 要求 `fiber.type` 不变。key 变了 → React 认为这是新组件 → 销毁旧的、创建新的 → 之前的 bailout 全部作废。

### 手法 6：Context 精细化——防止 Context 破坏 bailout ⭐⭐⭐

```jsx
// ❌ 一个大 Context 装所有状态
const AppContext = createContext()

function App() {
  const [theme, setTheme] = useState('dark')
  const [user, setUser] = useState({ name: 'Tom' })
  
  // 每次任何 state 变化，value 都是新对象
  // 所有消费者全部重新渲染
  return (
    <AppContext.Provider value={{ theme, user, setTheme, setUser }}>
      <Header />    {/* 只用 theme，但 user 变了也跟着渲染 */}
      <Profile />   {/* 只用 user，但 theme 变了也跟着渲染 */}
    </AppContext.Provider>
  )
}

// ✅ 拆成多个 Context
const ThemeContext = createContext()
const UserContext = createContext()

function App() {
  const [theme, setTheme] = useState('dark')
  const [user, setUser] = useState({ name: 'Tom' })
  
  return (
    <ThemeContext.Provider value={theme}>
      <UserContext.Provider value={user}>
        <Header />    {/* 只订阅 ThemeContext，user 变了不受影响 */}
        <Profile />   {/* 只订阅 UserContext，theme 变了不受影响 */}
      </UserContext.Provider>
    </ThemeContext.Provider>
  )
}
```

**为什么：** bailout 条件 2 要求 context 没有变化。一个大 Context 里任何字段变化，value 引用就变了 → 所有 Consumer 的 bailout 全部失败。拆成多个小 Context，每个 Consumer 只订阅自己关心的那个。

## 五、优化优先级排序（面试直接用）

```
优先级从高到低：

1. State 下沉（零成本，效果立竿见影）
2. 组件提升 / children 模式（零成本，架构调整）
3. EagerState（意识到 state 用原始值 vs 对象的差异）
4. Context 拆分（中等成本，全局受益）
5. React.memo + useMemo + useCallback（有成本，对症下药）
6. Key 稳定（基本功，应该一直做对）

核心原则：
前三个是"调整结构让 bailout 自然发生"
后三个是"加 API 手动触发 bailout"
结构优化 > API 优化
```
