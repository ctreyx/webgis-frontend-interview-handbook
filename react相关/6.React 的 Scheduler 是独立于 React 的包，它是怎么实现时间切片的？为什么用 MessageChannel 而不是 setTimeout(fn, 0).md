# React 的 Scheduler 是独立于 React 的包，它是怎么实现时间切片的？为什么用 MessageChannel 而不是 setTimeout(fn, 0)？

# Scheduler 的核心思路是：把一个大任务拆成多个小片，每片执行完检查一次时间，超时就让出主线程，下一帧再继续。

每一帧 16.7ms（60fps）的分配：

├── 浏览器自己的工作（样式计算 / 布局 / 绘制）
├── React 执行任务（时间片，默认 5ms）
└── 剩余时间：空闲 / 用户交互响应

React 任务执行流程：

performWorkUntilDeadline()
↓
记录 deadline = currentTime + 5ms（时间片大小）
↓
workLoop()：循环执行任务
├── 执行一个任务单元
├── 检查 shouldYield()：currentTime >= deadline ?
│ 否 → 继续执行下一个任务单元
│ 是 → 停！让出主线程
└── 让出后，发一个 MessageChannel 消息
↓
下一帧 onmessage 触发
↓
继续 performWorkUntilDeadline()

# 为什么用 MessageChannel 而不是 setTimeout(fn, 0)

1. setTimeout(fn, 0) 的问题： 定时器嵌套超过5层后，最小延迟强制4ms，浏览器实际一层也有1ms，react一秒要调度很多次，如果用定时器会导致每次多浪费4ms，帧率下降
2. onmessage 的触发时机是在当前宏任务结束后，下一个宏任务开始前,没有 4ms 最小限制，实测延迟 < 1ms,属于宏任务（不是微任务，微任务会阻塞渲染）

setTimeout(fn, 0) 的问题：

规范规定：setTimeout 嵌套超过 5 层，最小延迟强制为 4ms
（浏览器实际实现里即使第一层也有 1ms 左右的延迟）

React 一秒内要调度很多次：
1000ms / (5ms时间片 + 4ms延迟) = 111次
vs
1000ms / 5ms = 200次

每次多浪费 4ms，累积下来帧率明显下降！

MessageChannel 的优势：

onmessage 的触发时机是在当前宏任务结束后，下一个宏任务开始前
没有 4ms 最小限制，实测延迟 < 1ms
属于宏任务（不是微任务，微任务会阻塞渲染）

# 为什么必须是宏任务，不能是微任务？

# // 微任务（Promise.then / queueMicrotask）在当前宏任务结束后立刻执行
c
# // 执行完所有微任务，浏览器才有机会渲染

# // 如果用微任务调度，React 连续执行，浏览器没有机会渲染 → 页面卡死！

# // 宏任务之间浏览器可以插入渲染，这是让出主线程的关键

宏任务 vs 微任务 时序对比：

宏任务（MessageChannel）✅
[React任务5ms] → [浏览器渲染] → [React任务5ms] → [浏览器渲染]
↑ 每个宏任务之间浏览器都能渲染，用户感觉流畅

微任务（Promise）❌
[React任务] → [微任务继续] → [微任务继续] → 浏览器没机会渲染！
↑ 微任务队列清空才轮到渲染，等同于同步阻塞

setTimeout ⚠️
[React任务5ms] → [4ms空等] → [React任务5ms] → [4ms空等]
↑ 浪费 4ms，高频调度下帧率损失明显
