## 题目回顾

> 四个 Vue3 独立系统，独立部署独立发版，共享登录态

---

## 完整回答示范

---

**第一点：方案选型与取舍**

针对这个场景，我会先评估三个方向：

**① Module Federation（首选）**

因为四个系统都是 Vue3 同技术栈，Module Federation 是成本最低的方案。核心原理是 Webpack/Vite 在运行时动态加载远程模块，不需要基座，不需要沙箱，组件和 Store 可以直接共享。

```
适合场景：同技术栈、需要共享组件或状态、团队协作开发
优势：无额外运行时开销、接入成本低、天然支持模块共享
缺点：技术栈必须统一、样式隔离需要自己处理
```

**② qiankun（次选，若有存量系统）**

如果后续可能接入技术栈不同的系统，或者有 jQuery 等存量项目，qiankun 更合适。它基于 single-spa，通过路由监听动态加载子应用，提供 JS 沙箱和样式隔离。

```
适合场景：多技术栈混杂、存量系统改造接入
优势：隔离能力强、生态成熟
缺点：vite 支持需要额外插件、接入成本比 MF 高、性能有沙箱开销
```

**③ wujie（隔离要求极高时）**

用 iframe 做天然隔离，样式和 JS 完全独立，但通信成本高，且 iframe 本身有白屏、SEO、弹窗定位等历史问题。

```
适合场景：安全隔离要求极高，比如嵌入第三方系统
优势：隔离最彻底
缺点：通信繁琐、用户体验有损
```

> **我的选择：** 当前四个系统都是 Vue3，优先用 Module Federation。如果后期有异构系统接入，再评估引入 qiankun 基座。

---

**第二点：登录态共享设计**

有两种方案，取舍如下：

```
方案一：localStorage 存 Token
  优点：实现简单，同主域直接共享
  缺点：存在 XSS 风险，JS 可直接读取 Token

方案二：httpOnly Cookie 存 Token（推荐）
  优点：JS 无法读取，防 XSS 攻击
  同主域 Cookie 天然共享，无需额外处理
  缺点：需要服务端配合，CSRF 需要额外防护（配合 SameSite）
```

> 后台管理系统我会选 **httpOnly Cookie**，安全性更高。如果是纯前端部署无法控制服务端，退而选 localStorage，但必须做好 XSS 防护。

跨域问题通过 **Nginx 统一代理到同一主域**解决：

```nginx
# 四个系统统一挂在同一主域下不同路径
ops.company.com      → 运营后台
ops.company.com/tour → 文旅大屏
ops.company.com/h5   → 移动端
```

---

**第三点：子应用通信**

按复杂度分三层：

```
① 简单状态（用户信息、权限、Token）
   → qiankun: initGlobalState
   → MF: 共享 Pinia Store，直接读取

② 跨应用事件通知（A 系统操作触发 B 系统刷新）
   → 发布订阅 EventBus，挂在 window 上
   → window.__APP_EVENT_BUS__.emit('order:update', data)

③ 复杂数据流
   → 考虑后端 WebSocket 广播，前端被动接收
   → 避免前端跨应用状态过于耦合
```

> postMessage 是 wujie / 原生 iframe 的通信方式，qiankun 用的是 `initGlobalState`，两者要区分清楚。

**结论句（面试收尾用）：**

> 「我的选型原则是**够用就好，不过度设计**。当前场景同技术栈、独立部署、共享状态，Module Federation 最匹配。微前端不是银弹，引入之前要评估团队维护成本，避免为了微前端而微前端。」
