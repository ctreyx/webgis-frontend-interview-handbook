> "闭包的本质要从执行上下文说起。每个执行上下文包含两个环境——LexicalEnvironment 存 let/const，VariableEnvironment 存 var。每个词法环境有一个 outer 指针指向外层环境，这就是作用域链的实现。
>
> 关键在于函数创建时，JS 引擎会把当前的词法环境引用保存到函数对象的 `[[Environment]]` 内部槽中。当这个函数被 return 到外部，它的 `[[Environment]]` 依然引用着定义时的词法环境，导致那个环境的 EnvironmentRecord 无法被 GC 回收，里面的变量就一直存活——这就是闭包。
>
> 所以闭包不是什么特殊语法，而是**词法作用域 + 函数作为一等公民 + 垃圾回收机制**三者结合的自然结果。
>
> 实际引擎实现上，V8 会做逃逸分析，只有被闭包真正引用的变量才会保留在堆上的 Context 对象中，没有被引用的变量正常回收，不会造成不必要的内存泄漏。"

## 一、执行上下文的结构

每当一个函数执行，JS 引擎会创建一个执行上下文（Execution Context），它的内部结构如下：

```js
ExecutionContext = {
  LexicalEnvironment,    // 词法环境（let/const/函数声明）
  VariableEnvironment,   // 变量环境（var 声明）
  ThisBinding            // this 指向
}
```

### 为什么要分 LexicalEnvironment 和 VariableEnvironment？

```js
function foo() {
  var a = 1          // → 存在 VariableEnvironment
  let b = 2          // → 存在 LexicalEnvironment
  const c = 3        // → 存在 LexicalEnvironment

  if (true) {
    var d = 4        // → 还是 VariableEnvironment（var 没有块级作用域）
    let e = 5        // → 新的 LexicalEnvironment（块级作用域）
  }
}
```

### 关键区别

| 环境 | 存储内容 | 作用域特点 |
|---|---|---|
| **VariableEnvironment** | `var` 和 `function` 声明 | 整个函数共享一个，不会因为 `{}` 块而创建新的 → 这就是为什么 var 没有块级作用域 |
| **LexicalEnvironment** | `let` / `const` 声明 | 每遇到一个 `{}` 块，就创建一个新的词法环境 → 这就是为什么 let/const 有块级作用域 |

## 二、词法环境的数据结构

```js
LexicalEnvironment = {
  EnvironmentRecord: {
    // 当前作用域里声明的所有变量
    // 类似一个 key-value 的表
    a: undefined,
    b: 10,
    fn: <function>
  },
  outer: <指向外层词法环境的引用>   // ← 这就是作用域链的本质
}
```

### outer 就是作用域链的实现方式

它是一条**单向链表**：

```
全局词法环境
  ↑ outer
函数A的词法环境
  ↑ outer
函数B的词法环境（B 在 A 内部定义）
```

> 变量查找时，沿着 `outer` 链一层层往上找，找到全局还没有就报 ReferenceError。

---

## 三、闭包的形成机制

函数在创建时，会把当前的词法环境引用保存到自己的 `[[Environment]]` 内部槽中。当这个函数被返回到外部执行时，它依然持有对创建时词法环境的引用，导致那个环境无法被回收——这就是闭包。

---

## 四、V8 引擎的优化：逃逸分析（加分项）

V8 实际执行时不会完全按规范来，有一个重要优化：**Context 对象 + 逃逸分析**。

```js
function outer() {
  let a = 1    // 被 inner 引用
  let b = 2    // 没有被任何闭包引用
  let c = 3    // 没有被任何闭包引用

  function inner() {
    console.log(a)
  }

  return inner
}
```

V8 不会把 outer 整个词法环境都保留，它会做**逃逸分析**：

```
// V8 分析发现：
// a → 被 inner 引用，会逃逸到外部 → 放到堆上的 Context 对象
// b → 没有被闭包引用 → 放在栈上，函数结束就回收
// c → 没有被闭包引用 → 放在栈上，函数结束就回收

// 最终 inner 的 [[Environment]] 指向的 Context 对象只包含 { a: 1 }
// b 和 c 已经被回收了，不会造成内存浪费
```

> **面试话术**："规范层面闭包会保留整个词法环境，但 V8 引擎做了逃逸分析优化——只有真正被闭包引用的变量才会被提升到堆上的 Context 对象中保留，没有被引用的变量依然在栈上分配，函数执行完就回收。所以现代引擎的闭包不会造成大面积内存泄漏，只保留必要的变量。这个可以在 Chrome DevTools 的 Scope 面板里验证，闭包里只能看到被引用的变量，看不到同作用域的其他变量。"
