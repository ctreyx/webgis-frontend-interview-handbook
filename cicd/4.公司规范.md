"我加入公司的时候，ESLint 和 husky 这些基础设施是有的，但代码规范不足。比如有些文件上千行没有拆分，缺少注释，变量命名随意，后期维护和新人上手都很困难。

所以我分几步推进：

第一步，建立 Code Review 机制。最开始合并主分支的 MR 我必须看，前期主要是统一规范意识。后面逐步放手，改成每个项目两个前端互相 Review——不只是检查代码质量，也能互相熟悉对方的业务，加深对项目的理解。Review 重点看四个方面：有没有内存泄露、有没有注释、大文件有没有拆分、命名是否规范。

管理上，我会定期抽查。发现问题会把案例贴到前端群里做分享，但不会说是谁的代码，保护大家面子。做得好的同事我会推荐公司每月的优秀员工，正向激励。

第二步，引入 CI/CD。人工 Review 有两个局限：靠自觉，忙的时候就跳过了；检查质量不稳定，有些人仔细有些人走过场。所以我把基础的检查写进 CI/CD 流水线——ESLint 规范检查、TypeScript 类型校验、构建验证，变成流程上的硬约束，不通过就合不了代码。

第三步，加入 AI 审核。ESLint 只能查语法层面的问题，定时器没清除、事件监听没移除这些语义层面的问题它查不出来。所以我在流水线里加了 AI 代码审查——把 git diff 喂给 LLM 做语义审查，补齐静态检查的盲区。

整个过程是从人工到半自动到自动化逐步演进的，不是一步到位。"
