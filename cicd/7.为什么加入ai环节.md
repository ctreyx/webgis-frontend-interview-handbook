


我进入思湃德后，发现团队之前没有统一的开发规范。有些文件上千行没有拆分，没有注释，逻辑也没有提取成 hook 或公共组件，后期维护和新人上手都很困难。所以我做的第一件事是建立制度——Code Review 机制、ESLint 规范、husky + lint-staged 提交前检查、组件拆分原则、hook 提取规范这些。前期合并主分支的 MR 我必须看，慢慢团队习惯就建立起来了。

但后来绍兴项目这个大屏项目上线后，在现场出现了页面越用越卡、甚至白屏的问题。排查下来是资源泄漏——定时器没清除、Cesium 地图没销毁、事件监听没移除。这个项目是政务大屏，7×24 常驻运行，页面切换、弹窗开合这些操作不断累积未释放的资源。

我统计了一下，194 个 Vue 组件，只有 51 个写了 onUnmounted，覆盖率只有 26%。Cesium Viewer 创建了 17 个只销毁了 13 个。这个问题光靠 Code Review 解决不了——它不是'写错了'，是'少写了一段'，人眼很容易滑过去。ESLint 也查不到，我翻了 eslint-plugin-vue 的规则列表，100 多条里没有任何一条是检查资源有没有清理的。

所以我在流水线里加入了 AI 校验环节。但不是把代码全量丢给 AI——我做了两层。第一层是确定性规则扫描，用正则检查 API 配对，有 setInterval 就必须有 clearInterval，覆盖七类资源，扫全仓库 710 个文件只要 400 多毫秒，零成本。第二层才是 AI 语义审查，只审第一层筛出来的可疑文件——因为有些清理操作写在别的文件里、或者封装在工具函数里，正则判不了，需要 AI 理解上下文。

同时我之前定的规范——逻辑要提取 hook、公共组件要封装、单文件不能超过多少行——这些也能通过 AI 审查每次提交的 diff 来检查。相当于把之前靠人自觉执行的软约束，变成了流水线里的硬约束。

当然 AI 会误报，有些地方确实不好抽离逻辑，有些代码并不存在泄漏但 AI 还是标记了。所以我做了忽略文件，可以忽略掉特定的代码段，但必须写上注释说明为什么忽略、谁加的、什么时候过期，方便后续回溯。

这套方案最开始只在绍兴项目这一个项目上实验，效果不错——扫出了 58 处可疑，其中一个是真实的 high 级定时器泄漏，之前 Code Review 和 ESLint 都没发现。验证有效后，我逐步推广到了其他项目。



# ai 误报怎么办

做了忽略文件，但有几个设计原则。第一，忽略的粒度是代码行级别不是文件级别，用内容哈希而不是行号——行号会因为文件改动而漂移，哈希不会。第二，每条忽略必须写注释说明为什么忽略、谁加的、什么时候过期。第三，忽略文件本身在 Git 里管理，新增忽略条目会出现在 MR 的 diff 里，Code Review 时我会重点看。最重要的是：忽略只能豁免 AI 的判断，第一层规则扫描发现的问题是硬阻断，没有任何绕过方式
