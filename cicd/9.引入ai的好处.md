# 你觉得这套方案最大的价值是什么？不是技术层面的，是对公司和团队层面的。




我加入公司后做的第一件事是建立制度——Code Review、开发规范、hook 提取原则、组件拆分标准。前期效果很明显，团队代码质量确实提高了，但有一个问题始终解决不了——标准不统一。我 Review 的时候会检查定时器有没有清除、逻辑该不该提取 hook、组件该不该拆分，但我不可能每个项目每次 MR 都看。其他人 Review 的时候关注点不一样，有人看得细有人走过场，同样的问题这次被发现下次就漏掉了。绍兴大屏项目上线后出了资源泄漏导致卡顿白屏，这就是靠人盯没盯住的典型案例。

 

在没有 AI 之前，我也想过用 ESLint 硬约束来兜底，但很快发现行不通。比如地图大组件确实行数超千行，你设了 max-lines 500 它就报错，但你让开发者怎么拆？强行拆分变量互相引入只会造成冗余代码更难维护。ESLint 是死规则，不理解业务上下文，很多地方只能放开规则，放开了就等于没有。



AI 改变了这个局面。它能理解上下文——这个组件 五六百行 是因为职责确实复杂，还是因为混了不相关的逻辑该拆分？这个定时器是全局的不需要清理，还是组件级的必须清理？这种判断力是 ESLint 和 Code Review 都给不了的。

而且 AI 校验是在流水线里自动跑的，不影响开发节奏。以前 Code Review 每次都要花时间，还降低项目进度。现在代码一提交就自动检查，开发者不需要等人 Review 才知道有没有问题。

对公司来说最直接的变化是：项目质量变得可预期了。不管是谁写的代码、谁 Review 的、项目多赶，质量标准是流水线定义的，不会因为人的状态波动而波动。这套方案在绍兴项目验证后推广到了其他项目线，新项目接入只需要改一个配置文件。

最终反映在两个结果上：一是线上问题减少了，客户反馈页面卡顿白屏的情况明显好转，直接体现在客户验收评分上；二是团队沉淀了一套可复用的质量基础设施，后面新人进来、新项目启动，不需要重新建规范、不需要老人反复盯，流水线自动兜底。



# 具体数据：

严格的前后对比数据我没有，因为多项目并行没有统一的度量基准。但效果体现在三个层面：

第一，拦截能力。规则层在绍兴项目扫出 58 处可疑，其中一个是真实的定时器泄漏——这个问题 Code Review 和 ESLint 都没发现过。如果等到线上才发现，现场排查加修复至少半天。

第二，效率释放。以前 Code Review 我要花大量时间检查定时器有没有清除、事件有没有解绑、文件行数合不合理，现在这些交给流水线，Review 聚焦在业务逻辑和架构设计上。

第三，客户反馈。大屏项目之前隔几周就有现场反馈页面越用越卡，门禁上线修复泄漏后，这类反馈基本没有了，直接体现在客户验收评分上。

如果要做更严格的量化，我会在流水线里记录每次拦截的类型和数量，按月出趋势报告。这是后续可以改进的方向




# bug 减少多少
bug 减少多少我没有精确数据，因为我们同时跑多个政府项目，没有统一的 bug 追踪系统做前后对比。

但有一个明确的事实：绍兴大屏上线后出现的卡顿白屏问题，根因就是资源泄漏。引入门禁后扫出了 58 处可疑，修复了其中包括 1 个真实的 high 级定时器泄漏。这类问题如果等到线上才发现，一次现场故障的排查加修复加重新部署，至少半天到一天。而流水线拦住的成本是零——代码提交时就报错了。

还有一个间接指标：客户反馈页面卡顿的次数明显减少了。之前隔几周就有一次，门禁上线后基本没再收到过这类反馈。
