# 企业级前端 CI/CD 流水线：完整校验清单

---

## 一个典型的企业级前端流水线长这样

```
push 代码
    ↓
① 代码质量检查（lint + format）
    ↓
② 类型检查（TypeScript）
    ↓
③ 单元测试
    ↓
④ 构建
    ↓
⑤ 构建产物分析
    ↓
⑥ 部署测试环境（自动）
    ↓
⑦ 部署生产环境（手动审批）
```

---

## 逐层拆解

### 第一层：代码质量检查

| 检查项 | 工具 | 作用 | 企业为什么要做 |
|--------|------|------|--------------|
| **ESLint** | eslint | 检查代码规范和潜在 bug | 统一团队代码风格，减少低级错误 |
| **Prettier** | prettier | 代码格式化检查 | 保证所有人提交的代码格式一致 |
| **Stylelint** | stylelint | CSS/SCSS 规范检查 | 避免样式冲突和冗余 |
| **Commitlint** | commitlint | Git 提交信息格式校验 | 保证 commit 信息规范，方便生成 changelog |

流水线里的写法：

```yaml
lint:
  stage: lint
  script:
    - npm run lint          # ESLint
    - npm run lint:style    # Stylelint
    - npx prettier --check "src/**/*.{ts,tsx,vue}"  # 格式检查
```

---

### 第二层：类型检查

| 检查项 | 工具 | 作用 |
|--------|------|------|
| **TypeScript 类型检查** | tsc --noEmit | 不生成文件，只检查类型错误 |

```yaml
type-check:
  stage: check
  script:
    - npx tsc --noEmit
```

**为什么单独跑**：ESLint 能检查部分类型问题，但不如 tsc 完整。有些类型错误 ESLint 检查不到，但 tsc 能。两者互补。

---

### 第三层：单元测试

| 检查项 | 工具 | 作用 |
|--------|------|------|
| **单元测试** | Vitest / Jest | 验证函数和组件逻辑是否正确 |
| **测试覆盖率** | c8 / istanbul | 检查测试覆盖了多少代码 |

```yaml
test:
  stage: test
  script:
    - npm run test -- --coverage
    - node check-coverage.js   # 覆盖率低于阈值就阻断
```

覆盖率门禁：

```javascript
// check-coverage.js
const coverage = require('./coverage/coverage-summary.json')
const threshold = 60  // 企业一般要求 60-80%

const lines = coverage.total.lines.pct
if (lines < threshold) {
  console.log(`❌ 覆盖率 ${lines}% 低于阈值 ${threshold}%`)
  process.exit(1)
}
console.log(`✅ 覆盖率 ${lines}%，达标`)
```

---

### 第四层：构建

| 检查项 | 工具 | 作用 |
|--------|------|------|
| **构建** | Vite / Webpack | 编译打包，验证能否成功构建 |
| **产物验证** | 脚本检查 | 确认 dist 目录存在且不为空 |

```yaml
build:
  stage: build
  script:
    - npm run build
    - |
      if [ ! -d "dist" ] || [ -z "$(ls -A dist)" ]; then
        echo "❌ 构建失败，dist 为空"
        exit 1
      fi
      echo "✅ 构建成功"
  artifacts:
    paths:
      - dist/
    expire_in: 1 week
```

---

### 第五层：构建产物分析

| 检查项 | 工具 | 作用 |
|--------|------|------|
| **包体积分析** | bundlesize / size-limit | 检查打包体积是否超标 |
| **依赖分析** | webpack-bundle-analyzer | 检查是否有不必要的大依赖 |

```yaml
bundle-check:
  stage: analyze
  script:
    - npx size-limit
```

size-limit 配置：

```json
// package.json
{
  "size-limit": [
    {
      "path": "dist/**/*.js",
      "limit": "500 KB",
      "gzip": true
    }
  ]
}
```

**超过 500KB 就阻断**，防止有人不小心引入了一个巨大的三方包把打包体积撑爆。

---

### 第六层：安全检查（中大型企业会做）

| 检查项 | 工具 | 作用 |
|--------|------|------|
| **依赖漏洞扫描** | npm audit / Snyk | 检查 node_modules 里有没有已知安全漏洞 |
| **敏感信息检测** | gitleaks / trufflehog | 检查代码里有没有泄露密钥、API Key |

```yaml
security:
  stage: check
  script:
    - npm audit --audit-level=high    # 高危漏洞阻断
    - npx gitleaks detect --source .  # 扫描密钥泄露
```

## 完整的企业级 `.gitlab-ci.yml`

把上面所有层整合到一起：

```yaml
stages:
  - check
  - test
  - build
  - analyze
  - deploy

# ① 代码质量检查
lint:
  stage: check
  script:
    - npm ci --prefer-offline --no-audit
    - npm run lint
    - npx prettier --check "src/**/*.{ts,vue}"

# ② 类型检查
type-check:
  stage: check
  script:
    - npm ci --prefer-offline --no-audit
    - npx tsc --noEmit

# ③ 单元测试 + 覆盖率
test:
  stage: test
  script:
    - npm ci --prefer-offline --no-audit
    - npm run test -- --coverage
  coverage: '/Lines\s*:\s*(\d+\.?\d*)%/'

# ④ 构建
build:
  stage: build
  script:
    - npm ci --prefer-offline --no-audit
    - npm run build
  artifacts:
    paths:
      - dist/
    expire_in: 1 week
  only:
    - master

# ⑤ 产物体积检查
bundle-size:
  stage: analyze
  script:
    - npx size-limit
  only:
    - master

# ⑥ 自动部署测试环境
deploy-staging:
  stage: deploy
  script:
    - rsync -azP --delete dist/ root@staging-server:/home/front/$CI_PROJECT_NAME
  environment:
    name: staging
  only:
    - master

# ⑦ 手动部署生产环境
deploy-production:
  stage: deploy
  script:
    - rsync -azP --delete dist/ root@prod-server:/home/front/$CI_PROJECT_NAME
  environment:
    name: production
  when: manual
  only:
    - master
```

> **工程化与 CI/CD**：基于公司自建 GitLab 搭建前端 CI/CD 流水线，覆盖 ESLint 代码检查、TypeScript 类型校验、单元测试及覆盖率门禁（≥ 60%）、Vite 构建、产物体积监控（size-limit 阈值 500KB）与多环境部署；feature 分支 push 后自动触发质量检查与构建验证，master 分支构建通过后自动部署至测试环境，生产环境需手动审批触发，保障发布安全性与代码质量。

## 面试时怎么说

> *"我们当时的流水线大概分五个阶段：*
>
> *第一阶段代码检查，ESLint 跑代码规范、Prettier 检查格式一致性、tsc --noEmit 做类型校验。这三个任何一个不通过，流水线直接阻断，代码不允许往下走。*
>
> *第二阶段跑单元测试，同时检查覆盖率，低于阈值也阻断。*
>
> *第三阶段构建，用 Vite 打包，构建完检查 dist 目录是否正常生成。*
>
> *第四阶段产物分析，用 size-limit 检查打包体积有没有超标。之前有一次有人引入了一个 2MB 的库，导致打包体积暴涨，就是这个阶段拦住的。*
>
> *第五阶段部署，测试环境自动部署，生产环境 when: manual 手动触发。"*

## 一个重要提醒

**你要根据当时的真实情况来写。**

如果当时确实没有做 TypeScript 类型检查和单元测试，可以这样说：

> *"当时流水线主要覆盖了 ESLint 检查、构建验证和多环境部署。回头看，还应该加上 TypeScript 类型校验、单元测试覆盖率门禁和产物体积监控。这些是我后来在新项目里补上的改进。"*

**坦诚说"当时没做但后来意识到了"，比编造"当时就做了"安全得多。面试官追问细节你才答得上来。**
