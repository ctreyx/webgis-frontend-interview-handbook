# Cesium 加载模型的所有方式 + 性能对比

## 总览

Cesium 主要支持两种模型加载方式：使用 3D Tiles 显示大面积建筑群，或加载 glTF 模型放置单个模型。

但完整来说，Cesium 支持的加载方式有 **6 种**，我按性能从高到低排列：

```
┌──────────────────────────────────────────────────────────┐
│                Cesium 模型加载方式全览                      │
├────────────────┬─────────────┬───────────────────────────┤
│ 加载方式         │ 适用场景     │ 性能量级                   │
├────────────────┼─────────────┼───────────────────────────┤
│ 1. 3D Tiles    │ 大规模城市   │ ★★★★★ 百万级              │
│ 2. Primitive   │ 大量几何体   │ ★★★★  万级                │
│ 3. glTF/glb    │ 单个模型     │ ★★★   单个~百级            │
│ 4. GPU实例化    │ 大量重复模型  │ ★★★★★ 万级（同模型）       │
│ 5. CZML        │ 时序动态     │ ★★★   千级                │
│ 6. KML/GeoJSON │ 矢量数据     │ ★★    千级以内             │
└────────────────┴─────────────┴───────────────────────────┘
```

## 一、glTF / glb —— 单个模型加载

### 什么是 glTF

glTF 是被广泛支持的高效实时渲染格式，也是 3D Tiles 内部使用的格式。作为 Khronos 标准，由 Cesium 团队参与共创，glTF 已经成为"3D 领域的 JPEG"。

### 体积优势

glTF 模型可以比 OBJ 或 COLLADA 格式小得多。glTF 几何数据通常比等效的 OBJ 小 50%，比 COLLADA 小 75% 以上。

### 加载方式

```js
// ============ 方式1：通过 Entity 加载（简单，有交互，性能一般）============
viewer.entities.add({
  position: Cesium.Cartesian3.fromDegrees(120.15, 30.27, 0),
  model: {
    uri: './model/building.glb',
    minimumPixelSize: 64,
    maximumScale: 2000,
    scale: 1.0,
    silhouetteColor: Cesium.Color.YELLOW,
    silhouetteSize: 2
  }
})

// ============ 方式2：通过 Model API 直接加载（底层，性能更好）============
const model = await Cesium.Model.fromGltfAsync({
  url: './model/building.glb',
  modelMatrix: Cesium.Transforms.eastNorthUpToFixedFrame(
    Cesium.Cartesian3.fromDegrees(120.15, 30.27)
  ),
  scale: 1.0,
  minimumPixelSize: 64
})
viewer.scene.primitives.add(model)
```

### glTF vs glb

```
┌──────────┬────────────────────────────────────────────┐
│ glTF     │ JSON 文本 + 外部 .bin + 外部纹理             │
│          │ 多文件，可读，方便调试                         │
├──────────┼────────────────────────────────────────────┤
│ glb      │ 所有数据打包成一个二进制文件                    │
│          │ 单文件，体积更小，网络请求少，生产环境首选        │
└──────────┴────────────────────────────────────────────┘
```

### 性能瓶颈

加载 7735 个极简 glTF 模型时只能达到约 10fps，而使用 Cesium 内置几何体生成相同数量的模型却能保持 60fps。

**原因：** 每个 `Model.fromGltf` 都是一个独立的渲染对象，有独立的 draw call、独立的 shader program、独立的 VBO，7000+ 个独立 draw call GPU 直接崩。

## 二、GPU 实例化（Instancing）—— 大量重复模型

### 核心思想

实例化是一种优化技术，能让你用单次 draw call 渲染一个模型的多个实例。Cesium 中的典型用例是高效渲染重复元素，如树木、车辆和卫星。

### 实现原理

实例化与批处理遵循类似的理念，目标是将所有逐实例信息放入顶点属性而不是 uniform。关键区别是你可以指定一个顶点属性为实例化的，意味着它每个实例推进一次而不是每个顶点。主要好处是内存节省——你可以将实例化属性与逐顶点属性分离。例如渲染 1000 棵树，可以用一个顶点缓冲存储模型的位置、法线和纹理坐标，另一个存储每个实例的变换。

### 两种实例化方案

**方案1：EXT_mesh_gpu_instancing（glTF 扩展，推荐）**

```js
// 在 glTF 文件中使用 EXT_mesh_gpu_instancing 扩展
// 把所有实例的变换矩阵写入 glTF 文件
// Cesium 加载后自动用 GPU Instancing 渲染

// 适用于 3D Tiles Next
// .i3dm 格式在新版本中用 EXT_mesh_gpu_instancing 替代
```

.i3dm 文件使用 EXT_mesh_gpu_instancing 进行实例化，使用 EXT_structural_metadata 存储批处理表。

**方案2：GeometryInstance 批处理（Cesium 内置几何体）**

```js
// 适用于 Cesium 内置几何体（Box, Cylinder, Ellipsoid 等）
// 所有实例合并成一个 Primitive，一次 draw call

const instances = []
for (let i = 0; i < 10000; i++) {
  instances.push(new Cesium.GeometryInstance({
    geometry: new Cesium.BoxGeometry({
      minimum: new Cesium.Cartesian3(-5, -5, -5),
      maximum: new Cesium.Cartesian3(5, 5, 5)
    }),
    modelMatrix: Cesium.Matrix4.fromTranslation(
      Cesium.Cartesian3.fromDegrees(
        120 + Math.random(),
        30 + Math.random(),
        0
      )
    ),
    attributes: {
      color: Cesium.ColorGeometryInstanceAttribute.fromColor(
        Cesium.Color.fromRandom()
      )
    }
  }))
}

viewer.scene.primitives.add(new Cesium.Primitive({
  geometryInstances: instances,
  appearance: new Cesium.PerInstanceColorAppearance()
}))
// 1万个几何体，1次 draw call
```

GeometryInstance 允许一个 Geometry 对象被放置在多个不同位置并独立着色。例如一个 BoxGeometry 可以被实例化多次，每个都有不同的 modelMatrix 来改变其位置、旋转和缩放。

### 性能对比

```
加载 1000 个相同模型：

方式                    │ Draw Call │  FPS   │ 内存
────────────────────────┼──────────┼────────┼──────
Entity + glTF           │  1000    │  ~5    │ 极高
Model.fromGltf 循环     │  1000    │  ~10   │ 高
GPU Instancing          │  1       │  ~60   │ 低
GeometryInstance 批处理  │  1       │  ~60   │ 低
```

### 注意事项

ModelInstanceCollection 在最新版本中已不再可用。它曾经在放置大量相同 glTF 模型时非常有用——性能出色，GPU 使用率低，draw call 少。

现在推荐用 **3D Tiles + EXT_mesh_gpu_instancing** 替代。

## 三、CZML —— 时序动态数据

### 什么是 CZML

使用 CZML 创建数据驱动的时序动态场景，并通过多段 CZML 流式传输大量时序动态数据。

超过 16,000 个被美国政府跟踪的太空物体，包括它们的位置、状态和趋势信息，被记录为 CZML 格式，增量加载并实时显示到 Cesium 虚拟地球中，利用了 CZML 的可流式传输特性。

### 加载方式

```js
// CZML 是 JSON 格式，描述随时间变化的实体
const czmlData = [
  {
    "id": "document",
    "version": "1.0"
  },
  {
    "id": "aircraft-1",
    "position": {
      "epoch": "2024-01-01T00:00:00Z",
      "cartographicDegrees": [
        0,   120.0, 30.0, 10000,   // t=0s
        60,  121.0, 30.5, 10500,   // t=60s
        120, 122.0, 31.0, 11000    // t=120s
      ]
    },
    "model": {
      "gltf": "./model/aircraft.glb",
      "scale": 1.0,
      "minimumPixelSize": 64
    }
  }
]

viewer.dataSources.add(Cesium.CzmlDataSource.load(czmlData))
```

### 性能特点

```
优点：
  ✅ 天然支持时间轴动画
  ✅ 可流式传输（增量加载）
  ✅ 单个 JSON 描述整个场景

缺点：
  ❌ 底层走 Entity API，有 Property 每帧计算开销
  ❌ 大量实体时（>5000）帧率下降明显
  ❌ 没有 LOD，不适合大规模静态场景
```

## 四、KML / GeoJSON —— 矢量数据

### 加载方式

```js
// KML
viewer.dataSources.add(Cesium.KmlDataSource.load('./data/regions.kml'))

// GeoJSON
viewer.dataSources.add(Cesium.GeoJsonDataSource.load('./data/stations.geojson', {
  stroke: Cesium.Color.BLUE,
  fill: Cesium.Color.BLUE.withAlpha(0.3),
  strokeWidth: 2
}))
```

### 性能特点

这些格式按原样托管，不经过 3D Tiles 切片管线。3D Tiles 可以用于流式传输大规模环境，而 GeoJSON、KML 和 CZML 则提供对环境中实体的细粒度控制。

```
优点：
  ✅ GIS 行业标准格式，数据源丰富
  ✅ 适合展示边界、区域、标注等矢量数据
  ✅ 开发简单，几行代码就能用

缺点：
  ❌ 底层全部走 Entity API → Property 每帧计算
  ❌ 没有 LOD，没有空间索引
  ❌ 超过几千个要素就开始卡
  ❌ 大数据量建议转成 3D Tiles
```

## 五、3D Tiles vs 其他方案 —— 核心差异

### 为什么 3D Tiles 性能碾压其他方案

通过在 3D Tiles 生态系统中使用 glTF，Cesium 能够简化接收 3D Tile 并用 WebGL 渲染的过程，使管线更加快速和简化，从而最大限度地减少客户端处理。

```
3D Tiles 独有的能力：

1. HLOD（分层细节）    → 其他方案都没有
2. 空间索引（BVH树）   → 自动裁剪不可见瓦片
3. 流式加载           → 按需请求，不一次性加载
4. 内存管理           → 自动卸载不在视野的瓦片
5. GPU Instancing     → 合并 draw call
6. Draco 压缩         → 几何数据压缩 80~90%
7. KTX2 纹理压缩      → GPU 直接解码
```

## 七、实际项目中怎么选（决策树）

```
你的数据是什么？
│
├─ 大规模城市/倾斜摄影/点云
│  → 3D Tiles（唯一选择）
│
├─ 单个精细模型（建筑/设备/车辆）
│  → glTF/glb + Model API
│
├─ 大量重复模型（树木/路灯/桩基）
│  → 3D Tiles + EXT_mesh_gpu_instancing
│  → 或 GeometryInstance 批处理（内置几何体）
│
├─ 带时间轴的动态轨迹（飞机/卫星/车辆）
│  → CZML（天然支持时序）
│
├─ 区域边界/标注/行政区划
│  → GeoJSON/KML（数据量小）
│  → 数据量大则转 3D Tiles
│
└─ 自定义大量几何体（格点/站点/标记）
   → PrimitiveCollection + GeometryInstance
   → 或 BillboardCollection/PointPrimitiveCollection
```

## 八、面试完整话术

> *"Cesium 加载模型主要有六种方式。3D Tiles 是大规模场景的唯一选择，有 HLOD、流式加载、空间索引、内存自动管理，能处理百万级三角面；glTF/glb 适合单个精细模型，glTF 是 3D Tiles 内部使用的格式，被称为'3D 领域的 JPEG'，glb 比 OBJ 小 50%，比 COLLADA 小 75%；大量重复模型用 GPU Instancing，核心是单次 draw call 渲染所有实例，内存只存一份几何数据加逐实例变换矩阵；时序动态数据用 CZML，支持增量流式加载，16000 个太空物体的实时追踪就是用 CZML 实现的；KML 和 GeoJSON 适合少量矢量数据，底层走 Entity API，超过几千个要素性能就不行了。*
>
> *性能差异核心在于 draw call 和 LOD。每个独立 glTF 模型是一次 draw call，7000 个模型就是 7000 次 draw call，帧率直接个位数。而 GeometryInstance 批处理或 GPU Instancing 把所有实例合并成一次 draw call，同样数量能稳定 60fps。3D Tiles 在此基础上还有 LOD 和空间裁剪，所以能处理百万级以上的数据。"*
