
# 大数据图层方案怎么选？VectorLayer / ImageCanvas / WebGLPointsLayer

> **核心结论**：气温格点图场景，首选 **ImageCanvas 自绘**；超大数据量（百万级）考虑 **WebGLPointsLayer**；**VectorLayer 直接排除**。

---

## 完整面试话术

> "上万格点我会排除 VectorLayer，因为每个 Feature 都是完整对象实例，有事件系统和属性监听，大量格点渲染每帧都要 O(n) 遍历计算样式，内存和帧率都扛不住。
>
> 气温格点图我首选 ImageCanvas 方案，本质是把渲染权交给自己，用 Canvas 2D API 直接绘制，整张图作为一个图片贴到地图上，没有 Feature 对象的开销，同时可以完全自定义色带映射和插值逻辑，灵活度最高。
>
> 如果数据量到百万级别，会考虑 WebGLPointsLayer，数据一次性上传 GPU 的 VBO，颜色在 Fragment Shader 里并行计算，CPU 几乎没有压力，但缺点是自定义插值需要写 GLSL Shader，成本更高。
>
> 我们项目里上万格点用 ImageCanvas 足够，结合 LUT 查找表做色带映射，Web Worker 做数据预处理，整体渲染性能是稳定的。"

---

## 方案一：VectorLayer（为什么排除）

### 底层原理

```js
// VectorLayer 每个格点都要这样创建
const feature = new Feature({
  geometry: new Point(coordinate),
  temp: 23.5
})
vectorLayer.getSource().addFeature(feature)
```

### 源码层面发生了什么

- OpenLayers 内部每个 Feature 都是一个对象实例，有自己的**事件系统、属性监听、样式计算**
- 渲染时走的是 `VectorRenderer`，每帧都要遍历所有 Feature，计算样式、转换坐标、绘制到 Canvas
- 上万个 Feature 意味着：
  - **内存**：上万个对象实例，每个都带事件监听，内存占用极大
  - **渲染**：每帧 O(n) 遍历，帧率直接崩
  - **垃圾回收**：大量对象频繁创建销毁，GC 压力大

> **面试话术**："VectorLayer 本质是面向交互设计的，每个 Feature 有完整的事件和属性系统，适合几百个可交互的矢量要素，用来做上万格点纯渲染是大炮打蚊子，性能不可接受。"

## 方案二：ImageCanvas（首选）

### 底层原理

```js
const imageCanvas = new ImageCanvasSource({
  // OpenLayers 每次视图变化，回调这个函数让你自己画
  canvasFunction: (extent, resolution, pixelRatio, size, projection) => {
    const canvas = document.createElement('canvas')
    canvas.width = size[0]
    canvas.height = size[1]
    const ctx = canvas.getContext('2d')

    // 把经纬度转成像素坐标
    data.forEach(point => {
      const pixel = map.getPixelFromCoordinate(
        fromLonLat([point.lng, point.lat])
      )
      
      // 直接用 Canvas 2D API 绘制
      ctx.fillStyle = getColorFast(point.temp, -10, 40)
      ctx.fillRect(pixel[0], pixel[1], gridSize, gridSize)
    })

    return canvas
  }
})

const layer = new ImageLayer({ source: imageCanvas })
```

### 源码层面发生了什么

- `ImageCanvasSource` 本质是把**渲染权交给你**，OpenLayers 只负责管理这张 Canvas 的生命周期
- 视图变化时触发 `canvasFunction` 回调，你拿到 extent 和 size 自己绘制
- 最终这张 Canvas 作为一个整体图片贴到地图上，不存在逐 Feature 的对象开销
- 渲染复杂度从 O(n) 对象管理，变成**一次性 Canvas 绘制**

### 优缺点

| 优点 | 缺点 |
|---|---|
| 完全自定义渲染逻辑，色带映射、插值都可以在这里做 | 无法直接交互（点击格点拿不到数据），需要自己计算坐标反查 |
| 内存占用只有一张 Canvas | 地图缩放时需要重新触发 `canvasFunction` 重绘 |
| 性能比 VectorLayer 好一到两个数量级 | |

## 方案三：WebGLPointsLayer（百万级）

### 底层原理

```js
import { WebGLPointsLayer } from 'ol/layer'

const layer = new WebGLPointsLayer({
  source: vectorSource,
  style: {
    symbol: {
      symbolType: 'square',
      size: 10,
      // 这里写的是 WebGL Shader 表达式
      color: [
        'interpolate',
        ['linear'],
        ['get', 'temp'],
        -10, 'blue',
        15,  'green', 
        40,  'red'
      ]
    }
  }
})
```

### 源码层面发生了什么

- `WebGLPointsLayer` 底层走的是 **WebGL 渲染管线**，数据上传到 GPU 的 VBO（顶点缓冲区）
- 每个格点是一个顶点，颜色计算在 **Fragment Shader 里并行执行**
- CPU 只负责一次性上传数据，之后渲染全部在 GPU 完成
- 理论上支持**百万级**的点，帧率依然流畅

---

## 三方案选择依据总结

| 场景 | 推荐方案 |
|---|---|
| 上万格点 + 自定义色带 + 需要平滑插值 | **ImageCanvas** |
| 百万级格点 + 简单样式 + 不需要插值 | **WebGLPointsLayer** |
| 需要点击交互 | **WebGLPointsLayer**（有 hit detection） |
| 几百个可交互矢量要素 | **VectorLayer**（面向交互设计的本质场景） |
