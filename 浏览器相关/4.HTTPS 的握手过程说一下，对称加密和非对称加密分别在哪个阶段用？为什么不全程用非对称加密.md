# HTTPS 的握手过程说一下，对称加密和非对称加密分别在哪个阶段用？为什么不全程用非对称加密？

过程：

客户端推送 1. 首先客户端需要向服务端推送信息，携带 ： TLS版本（目前2个版本，1.2 和 1.3 客户端携带自己版本问服务端），随机数，密码套件列表（哈希算法，秘钥算法等）

服务器接受 2. 接受后选择一个tls版本，密码套件，并且生成自己的随机数 . 然后 发送 服务器公钥，证书域名，证书有效期，证书签名，

客户端接受 3. 客户端需要先验证服务器的证书有效性。 然后发送RSA秘钥（客户端生成一个随机数，用服务器的公钥加密后发给服务器） 或者 DHE/ECDHE秘钥

服务器接受 4. 用私钥解密pre-master secret或者直接用共享密钥 解密。 然后发送 两段随机数 解密秘钥生成会话秘钥

现在完成，后续用会话秘钥进行加密后续http数据

TLS 握手更准确的流程：

1. Client Hello：客户端发送
   - TLS版本、随机数A、支持的密码套件

2. Server Hello：服务器发送
   - 选定TLS版本、随机数B、证书（含公钥）

3. 客户端验证证书
   - 验证CA签名是否合法
   - 生成随机数C（pre-master secret）
   - 用服务器公钥加密随机数C → 发给服务器
     ← 这里用了非对称加密！

4. 两端各自用 随机数A + B + C
   生成相同的会话密钥（对称密钥）
   ← 后续通信用对称加密！

为什么不全程用非对称加密：
非对称加密计算量极大，慢10-100倍
对称加密速度快，适合大量数据传输
所以：非对称用来安全交换密钥，对称用来加密数据
