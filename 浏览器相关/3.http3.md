# HTTP3

HTTP2 解决了应用层的队头阻塞，但 TCP 本身的队头阻塞还在。HTTP3 把 TCP 换成了 QUIC（基于 UDP），在传输层彻底解决了队头阻塞。

## 关键问题

HTTP2：虽然应用层并行了，但底层还是一条 TCP 连接。TCP 保证有序可靠交付，一个包丢了 → 后面所有包等重传。

## 队头阻塞有两个层面

### 应用层队头阻塞（HTTP 协议层）

```text
HTTP1.1：同一个 TCP 连接，请求必须串行
请求 A 没返回，请求 B 不能发
→ 应用层队头阻塞

HTTP2：多路复用，多个 Stream 并行
→ 应用层完全没有队头阻塞 ✅
```

### 传输层队头阻塞（TCP 协议层）

```text
HTTP2：虽然应用层并行了，但底层还是一条 TCP 连接
TCP 保证有序可靠交付，一个包丢了 → 后面所有包等重传
→ 传输层队头阻塞依然存在 ❌

HTTP3：换掉 TCP，用 QUIC
→ 传输层队头阻塞彻底解决 ✅
```

## 本质原因

- HTTP2 在应用层实现了 Stream 多路复用
- 但多个 Stream 的数据都塞进同一条 TCP 字节流里传输

TCP 不知道 Stream 的概念。
TCP 只知道：这是一段字节流，必须保证按序到达。
一个字节丢了 → 后面所有字节都等 → 所有 Stream 一起等。

应用层的并行，在 TCP 层面看来还是一条串行字节流。
这是根本矛盾，HTTP2 无法在 TCP 上解决这个问题。

## 丢包率对 HTTP2 的影响

研究数据（Google QUIC 论文）：

- 丢包率 0%：HTTP2 比 HTTP1.1 快 ~40%
- 丢包率 2%：HTTP2 和 HTTP1.1 性能持平
- 丢包率 > 2%：HTTP2 比 HTTP1.1 更慢！

为什么丢包高时 HTTP2 反而更慢？

- HTTP1.1：6 条 TCP 连接，一条丢包只影响这条连接上的请求
- HTTP2：1 条 TCP 连接，丢包影响所有 Stream

弱网环境（移动网络 / 高丢包场景）下，HTTP2 的优势反而变成了劣势。

## 一句话总结三代进化

| 协议    | 核心特征                                    | 队头阻塞情况                                                   | 备注                                                                                             |
| ------- | ------------------------------------------- | -------------------------------------------------------------- | ------------------------------------------------------------------------------------------------ |
| HTTP1.1 | 文本协议，串行请求                          | 应用层 + 传输层都有队头阻塞                                    | -                                                                                                |
| HTTP2   | 二进制 + 多路复用                           | 解决应用层队头阻塞；传输层仍有 TCP 队头阻塞                    | 弱网丢包时甚至比 HTTP1.1 更差                                                                    |
| HTTP3   | 换掉 TCP，用 QUIC（UDP + 用户空间可靠传输） | Stream 独立管理，丢包只影响对应 Stream，传输层队头阻塞彻底解决 | 连接建立更快（0 RTT），网络切换无缝迁移；代价是 UDP 在某些网络设备上被限速/屏蔽，部署比 HTTP2 难 |
