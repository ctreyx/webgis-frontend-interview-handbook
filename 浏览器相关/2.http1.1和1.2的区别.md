# HTTP2 vs HTTP1.1 —— 面试版

HTTP1.1 最大的问题是队头阻塞，一个连接同一时间只能处理一个请求。HTTP2 用二进制分帧 + 多路复用彻底解决了这个问题，一个连接可以并行处理无数个请求。

# 重点 http2 解决的是1.1的队头阻塞，并没有解决tcp的队头阻塞，需要等到1.3才能解决tcp

# 总结

http1.1，同一个tcp发送2个请求，第一个长，第二个短，就算第二个处理很快，也必须等第一个响应后。

HTTP2 解决了应用层的队头阻塞，但 TCP 本身的队头阻塞还在。HTTP3 把 TCP 换成了 QUIC（基于 UDP），在传输层彻底解决了队头阻塞。

## HTTP1.1 的核心问题

HTTP1.1 的请求模型：

```text
TCP连接1: [请求A ──────响应A] [请求B ──────响应B] ← 串行！
TCP连接2: [请求C ──────响应C] [请求D ──────响应D]
TCP连接3: [请求E ──────响应E] [请求F ──────响应F]
```

浏览器对同一域名最多开 6 个 TCP 连接（各浏览器略有不同）。
每个连接串行处理请求 → 队头阻塞（Head-of-Line Blocking）。

### 问题

- 请求A 响应慢 → 后面所有请求都要等 → 整体延迟高
- 6个连接不够 → 第 7 个请求必须等前面某个连接空出来

## HTTP1.1 的优化手段（都是在打补丁）

1. 域名分片（Domain Sharding）
   把资源分散到多个子域名。
   `tile1.map.com / tile2.map.com / tile3.map.com`
   每个域名 6 个连接 → 变相突破 6 连接限制。
   副作用：DNS 解析开销、TCP 握手开销增加。

2. 资源合并（Bundling）
   JS/CSS 打包成一个大文件 → 减少请求数。
   副作用：改一行代码整个包缓存失效。

3. 雪碧图（Sprite）
   把小图标合并成一张大图。
   副作用：维护麻烦，单个图标无法缓存。

4. keep-alive
   复用 TCP 连接，不用每次握手。
   但连接内部仍然串行，没解决队头阻塞。

## HTTP2 的核心改变

1. 改变一：二进制分帧（Binary Framing）
   所有数据拆成二进制帧（Frame）。
   每个帧有 stream_id 标识属于哪个请求。

2. 改变二：多路复用（Multiplexing）★ 最核心
   多个请求的帧交错发送，接收端按 stream_id 重新组装。
   一个连接，无限并发，彻底消灭队头阻塞（应用层）。

3. 改变三：头部压缩（HPACK）
   请求1：发完整头部，建立动态表。
   请求2：只发变化的部分（比如只有 path 变了）。
   `"path: /tile/2/2/3.png"`（其他头部用索引代替）。

实测：头部体积减少 85%~90%。

4. 改变四：请求优先级（Stream Priority）
   可以给每个 Stream 设置优先级。
   关键资源（HTML/CSS）→ 高优先级，优先传输。
   图片/瓦片 → 低优先级，后传输。

对地图场景：

- 视口中心的瓦片 → 高优先级
- 边缘瓦片 → 低优先级
- 预加载瓦片 → 最低优先级

## HTTP1.1 vs HTTP2 对比

| 维度       | HTTP1.1            | HTTP2                    |
| ---------- | ------------------ | ------------------------ |
| 协议格式   | 文本               | 二进制                   |
| 连接复用   | keep-alive（串行） | 多路复用（并行）         |
| 并发请求   | 6个TCP连接         | 1个TCP连接无限并发       |
| 队头阻塞   | 有（应用层）       | 无（应用层）             |
| 头部处理   | 完整文本重复发送   | HPACK压缩，增量发送      |
| 服务端推送 | 不支持             | 支持                     |
| 请求优先级 | 不支持             | 支持                     |
| TLS        | 可选               | 实践上必须（浏览器强制） |
| 域名分片   | 需要（打补丁）     | 反而有害（破坏多路复用） |

## HTTP2 对地图瓦片加载的影响

### 1) HTTP1.1

- 某个瓦片响应慢 → 该连接其他瓦片全部阻塞
- 连接建立有 TCP 握手 + TLS 握手开销（每个域名）
- 为突破 6 连接限制，用了域名分片（tile1/tile2/tile3.map.com）
- 额外 DNS 解析 + 握手开销

### 2) HTTP2 加载瓦片的优势

单个TCP连接，20个Stream并行：

```text
Stream1:  瓦片1  ──────────────────▶
Stream2:  瓦片2  ────────────────▶
Stream3:  瓦片3  ──────────────────────▶
...
Stream20: 瓦片20 ──────────────▶
```

- 某个瓦片响应慢 → 只影响它自己，其他瓦片不受影响 ✅
- 1次TCP握手 + 1次TLS握手，连接复用 ✅
- HPACK 压缩：瓦片请求头高度相似（host/path 几乎一样）
- 压缩率极高，头部开销趋近于零 ✅

## 总结

HTTP2 对地图瓦片的实际收益：

- ✅ 一个连接并行加载所有瓦片，消灭 6 连接限制
- ✅ 头部压缩，瓦片请求头相似度高，压缩率极高
- ✅ 不需要域名分片，减少 DNS + TCP + TLS 握手开销
- ✅ 优先级控制，视口内瓦片优先加载

注意点：

- ⚠️ 弱网丢包时，TCP 队头阻塞会影响所有 Stream
- ⚠️ 需要 TLS（浏览器实践要求），但本身 TLS 也是必要的

HTTP1.1 → HTTP2 瓦片加载速度提升：

- 正常网络：提升 20%~40%（减少握手+头部压缩）
- 高并发场景：提升更明显（多路复用消灭等待）
- 弱网丢包：可能不如 HTTP1.1 多连接（TCP队头阻塞）
