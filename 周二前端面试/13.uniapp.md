### 一、完整高分口述版（约 2 分 30 秒，正式面试优先用这个）

“我在项目中用 UniApp 做过小程序 + H5 + App 的多端交付，主要目标是一套代码覆盖多端，大幅降低重复开发成本，同时支撑快速交付。

**1. 选型理由与对比**  
团队是 Vue 技术栈，UniApp 基于 Vue 语法，学习成本最低，一套代码可同时输出微信/支付宝等小程序、H5、App（iOS/Android），甚至支持鸿蒙。  
对比：  
- 原生小程序：各端单独写，维护成本高，适合单端极致性能；  
- Taro：更适合 React 团队，运行时方案包体积和性能略有差异；  
- Flutter：App 性能最强（自绘引擎），但对小程序支持弱，团队技术栈不匹配。  
我们选 UniApp 是追求**交付效率和多端一致性**，支付、登录、分享等能力各端不同，需要额外适配，这是它的主要短板，但整体性价比最高。

**2. 核心原理（编译时 + 运行时双引擎）**  
UniApp 本质是「**编译器 + 多端运行时**」：  
- **编译时**（HBuilderX 或 uni-cli，Vue3 用 Vite，Vue2 用 Webpack）：把 .vue 文件翻译成各端能懂的代码。  
  - 小程序 → 拆成 wxml/wxss/js/json；  
  - H5 → 标准 HTML/JS/CSS；  
  - App → js（vue 页面走 webview）或原生（nvue/uts 编译成 Kotlin/Swift）。  
  核心武器是**条件编译**（`#ifdef MP-WEIXIN` / `#ifndef APP-PLUS` / `#endif`），在编译阶段直接把不需要的代码剥离，产物干净，无运行时 if 判断开销。  
- **运行时**：  
  - 提供 `uni.xxx` 统一 API（request、login、storage 等），在不同端做 polyfill 映射到原生能力；  
  - 非 H5 端（小程序/App）是**逻辑层与视图层分离的双线程模型**（和微信小程序一样），通过 JSBridge 通信；  
  - App 端默认 webview 渲染，性能敏感页面可用 **nvue**（原生渲染，类似 Weex）或新的 **uni-app x**（UTS 更接近原生）。  

所以它不是简单的运行时翻译，而是**编译期解决大部分平台差异**，运行时只做业务逻辑和桥接，这是高效的关键。

**3. 实际架构与 monorepo 结合**  
我们把 UniApp 项目放进 pnpm monorepo 统一管理：  
- `packages/shared` 或 `uni_modules`：放可复用组件、hooks、工具（目标 60%+ 复用）；  
- `packages/api`、`stores`（Pinia）；  
- **platform-adapt 适配层**：专门处理登录、支付、分享、权限等差异，用条件编译或策略模式封装，对外提供统一调用；  
- pages 强制分包，控制小程序主包体积（通常压到 1.5M 以内）。  

H5 端产物可以直接作为 qiankun 子应用嵌入主系统，实现「多端 + 微前端」打通。新项目很多页面直接复用 monorepo 组件和 hooks，启动时间明显缩短。

**4. 常见坑与治理**  
- 条件编译写错 → 白屏或功能缺失，靠 CR + AI 语义门禁检查；  
- rpx 在不同端表现差异 → 统一设计稿基准 + 关键页面真机调试；  
- 小程序主包超 2M → 强制分包 + 异步组件 + 图片 CDN；  
- 登录/支付各端逻辑不同 → 全部收口到 platform-adapt 层；  
- App 端 vue 页面卡顿 → 长列表/复杂动画改 nvue 或虚拟列表；  
- nvue 与 vue 混用样式/通信问题 → 尽量减少混用，能 vue 就 vue。  

质量上复用之前的 AI + CI 门禁（规范、重复造轮子、条件编译正确性），Storybook 类文档也沉淀。

**总结**  
UniApp 对我来说是「用编译时差异处理换多端交付效率」的方案。结合 monorepo 组件资产化 + 适配层 + 条件编译，既能保证 60% 以上复用，又能支撑小程序/H5/App 同时交付，H5 还能进 qiankun。最终目标还是提升项目交付速度和团队资产沉淀，匹配既有自研产品又有交付项目的岗位需求。”

### 二、关键原理深度补充（面试官能追问的点，你必须懂）

**1. 条件编译到底怎么工作？**  
- 语法：`// #ifdef MP-WEIXIN` … `// #endif`（js）、`<!-- #ifdef H5 -->`（template）、`/* #ifdef APP-PLUS */`（css）  
- 原理：编译器（@dcloudio 插件）在编译阶段用正则匹配这些注释，**只保留目标平台代码，其他直接删除**，不是运行时 if。  
- 好处：包体积小、无多余分支、安全性高（不会把其他端 API 编译进去报错）。  
- 常用标识：`H5`、`MP-WEIXIN`、`MP-ALIPAY`、`APP-PLUS`、`APP-PLUS-NVUE`、`MP`（所有小程序）等。

**2. 双线程模型（小程序/App vue 页面）**  
- 逻辑层（JS）和渲染层（原生/WebView）分离。  
- 数据变更通过 `setData`（或 uni 封装）桥接，有序列化成本。  
- 所以长列表、频繁更新要优化（虚拟列表、分页、减少 setData 数据量）。

**3. vue 页面 vs nvue vs uni-app x**  
- vue 页面：WebView 渲染，CSS 灵活，开发快，但 App 端性能一般。  
- nvue：原生渲染（flex 布局为主），App 长列表/动画更流畅，但 CSS 支持有限。  
- uni-app x：新一代，UTS 编译成真正原生（Kotlin/Swift），性能接近原生，是未来方向。

**4. 编译产物差异**  
- 小程序：真正生成各平台小程序代码。  
- H5：标准 Vue SPA + uni runtime（可 tree-shaking）。  
- App：打包成 wgt 或云打包成安装包，可热更新。

### 三、高频追问 & 高分答法（一定要练）

**Q1：条件编译和运行时 if (process.env.VUE_APP_PLATFORM) 有什么区别？**  
A：条件编译是编译期删除代码，产物干净、无性能开销、更安全；运行时 if 会把所有代码都打进去，包体积大，还可能在不支持的端报错。优先条件编译，实在动态再用运行时判断。

**Q2：为什么小程序有双线程？对性能有什么影响？**  
A：为了安全和性能隔离（逻辑层不能直接操作 DOM）。代价是通信有序列化成本，所以要少 setData、用虚拟列表、数据分页。

**Q3：App 端如何提升性能？**  
A：长列表/复杂动画用 nvue 或 uni-app x；减少 DOM 层级；图片压缩 + WebP + CDN；分包；首页骨架屏；避免频繁 uni API 调用。实测首页 nvue 可把启动压到 1s 左右。

**Q4：如何与 monorepo 结合？组件怎么复用？**  
A：shared/uni_modules 放通用组件 hooks；platform-adapt 层封装差异；H5 产物可直接当 qiankun 子应用；AI + CI 检查是否重复造轮子、条件编译是否正确。

**Q5：登录/支付怎么优雅处理多端差异？**  
A：全部收口到 platform-adapt 服务，对外提供 `login()`、`pay()` 统一方法，内部用条件编译或策略模式调用各端原生 API。业务代码无感知。

**Q6：小程序主包体积超限怎么办？**  
A：强制分包（pages.json subPackages）、异步组件、图片/字体上 CDN、去掉无用插件和 polyfill、开启 tree-shaking。

**Q7：H5 如何嵌入 qiankun？**  
A：H5 打包成独立资源，entry 指向完整地址，处理好 publicPath（和之前 qiankun 一样），用 `__POWERED_BY_QIANKUN__` 判断环境，导出生命周期。

**Q8：nvue 和 vue 混用有什么坑？**  
A：样式不互通、通信成本高、页面切换可能闪屏。建议同一业务流尽量统一渲染模式，能 vue 就 vue，性能敏感再用 nvue。

**Q9：uni-app x 了解吗？什么时候用？**  
A：了解，它用 UTS 编译成真正原生代码，性能接近原生，适合对 App 体验要求极高的新项目。现有项目可渐进迁移核心页面。

**Q10：如何保证多端质量？**  
A：真机 + 模拟器双测、条件编译 AI 检查、主流程自动化回归、各端单独的 UI 快照/视觉回归（如果有）、文档沉淀平台差异。
