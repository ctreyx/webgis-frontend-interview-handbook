# qiankun 的沙箱隔离


# 沙箱js
qiankun 的 JS 沙箱主要解决子应用之间、子应用和主应用之间的 window 全局变量污染问题。它提供了三种，默认用的是 ProxySandbox，另外两种做兼容。

先说 SnapshotSandbox（快照沙箱）：它是单实例的。子应用 mount 之前，先把真实 window 的属性做一份快照；子应用运行时可以随意修改 window；unmount 的时候对比差异，把新增的删掉、改过的还原回去。实现简单，兼容性好，但因为直接污染了真 window，所以只能同时跑一个子应用，属性多的时候还原也有开销。

而默认的 ProxySandbox 是多实例的，思路完全不一样：它从一开始就不污染真实 window。给每个子应用创建一个 fakeWindow（空对象），再包一层 Proxy。get 的时候优先从 fakeWindow 取，没有再代理到真实 window；set 的时候全部写到 fakeWindow 里。这样每个子应用都有自己独立的代理 window，互相不影响，也支持多个子应用同时激活。unmount 时直接丢弃这个 fakeWindow 就行，不用做 diff 还原，性能更好。

子应用的 JS 是怎么进到沙箱里执行的呢？qiankun 通过 HTML Entry 拿到 script 后，会把代码包一层，大致是：
```js
(function (window) {
  with (window) {
    /* 原代码 */
  }
}).bind(proxy)(proxy);
```

用 with + bind 到 proxy，让代码里的全局操作都走到我们的代理上。

在我之前的天府科技项目里，开发态、运行态、运维态三个平台互相嵌入，特别是开发态改完要实时预览运行态页面，就会同时存在多个子应用，所以必须用 ProxySandbox 的多实例能力。我们还把公共的 React/Vue 等通过 externals 抽到主应用，避免每个沙箱重复加载。样式上开启了 Shadow DOM，弹窗问题就通过挂载到主应用 body 解决。

总结一下：Snapshot 是"污染后还原"，适合单实例老环境；Proxy 是"从头隔离"，支持多实例，是现在的默认和推荐。理解这两种思路，基本就能把 qiankun 的沙箱讲清楚了。

## 一、原理速记（先学清楚，再口语化）

qiankun 的 JS 沙箱主要有三种，默认是 ProxySandbox（支持多实例），另外两个是兼容/降级。

### ① SnapshotSandbox（快照沙箱，单实例）

**思路：** 先污染，再还原。

**流程：**

- 子应用 mount 前，把当前真实 window 的所有属性做一份快照（shallow copy）。
- 子应用正常跑，随便改 `window.xxx`。
- unmount 时，对比当前 window 和快照的差异：新增的删掉、修改的改回去、删除的补回来。

**优点：** 实现简单，兼容性好（不需要 Proxy，IE 都能用）。

**缺点：** 只能单实例（因为改的是真 window），属性多的时候 diff 还原有性能开销。

### ② LegacySandbox（遗留沙箱，也是单实例）

用 Proxy 记录所有修改到一个 Map 里，unmount 时按记录还原。比 Snapshot 更精确，但仍是单实例。

### ③ ProxySandbox（代理沙箱，默认，多实例）← 重点

**思路：** 从一开始就隔离，根本不污染真实 window。

**核心实现：**

```js
// 伪代码（面试能写出来就加分）
class ProxySandbox {
  constructor() {
    this.fakeWindow = Object.create(null); // 空对象当假window
    this.proxy = new Proxy(this.fakeWindow, {
      get: (target, prop) => {
        // 优先从 fake 取，没有再从真实 window 取（白名单/特殊处理除外）
        if (prop in target) return target[prop];
        const value = window[prop];
        // 函数需要绑定 this 等处理
        return typeof value === 'function' ? value.bind(window) : value;
      },
      set: (target, prop, value) => {
        // 所有写入都进 fakeWindow，绝不碰真 window
        target[prop] = value;
        return true;
      },
      has: (target, prop) => prop in target || prop in window,
      // 还有 deleteProperty、getOwnPropertyDescriptor 等
    });
  }
  active() {
    /* 激活 */
  }
  inactive() {
    /* 失活，直接丢弃 fake 即可，不用还原 */
  }
}
```

每个子应用 new 一个自己的 ProxySandbox，互不影响 → 天然多实例、支持同时激活多个子应用。

**优点：** 隔离彻底、性能好（不用 diff 还原）、支持多实例。

**缺点：** 需要 Proxy（现代浏览器），对 eval、with、某些原生 API 要额外处理。

### JS 代码到底怎么被放进沙箱执行的？

qiankun 拿到 script 内容后，会包一层，大致是：

```js
(function (window, self, globalThis) {
  with (window) {
    // 这里是子应用原来的 JS 代码
    // 所有对 window 的读写都会走到 Proxy 的 get/set
  }
}).call(proxy, proxy, proxy, proxy);
// 或者用 new Function + with 的方式
```

用 `with(proxy)` + bind/call 到 proxy，让代码里的自由变量查找和 window 操作都走代理。这就是"让子应用以为自己在操作 window，其实操作的是 fakeWindow"。

### 样式隔离（顺带记）

严格模式 Shadow DOM；实验性 scopedCSS（选择器加前缀）；关闭则无隔离。

# Shadow DOM 样式/DOM 隔离原理（完整学习版 + 面试可讲版）

1. 核心原理（先彻底搞懂）
Shadow DOM 是浏览器原生的封装边界（Web Components 标准的一部分）。

给一个普通元素（叫 shadow host）调用 element.attachShadow({ mode: 'open' | 'closed' })，就会创建一个隐藏的 shadow root。
这个 shadow root 下面可以挂一整棵独立的 DOM 树（shadow tree）。
隔离效果：
样式隔离（最重要）：
shadow 内部的 <style> 或 CSS 不会泄漏到外部（主应用/其他子应用）。
外部的全局 CSS 默认也进不来（不会影响 shadow 内部）。
只有通过特殊方式才能穿透：CSS 变量（--var）、::part()、::slotted()、:host 等。
DOM 隔离：
外部 document.querySelector 默认找不到 shadow 内部的元素。
内部的 JS 操作也主要局限在自己的树里。
模式区别：
open：主应用可以通过 host.shadowRoot 访问内部（qiankun 等常用这个，方便调试和操作）。
closed：shadowRoot 返回 null，更严格，外部几乎无法访问。
简单伪代码示意：

JavaScript

const host = document.getElementById('subapp-container');
const shadow = host.attachShadow({ mode: 'open' });

// 把子应用的 HTML 和 CSS 都放进 shadow 里
shadow.innerHTML = `
  <style>
    /* 这些样式只在 shadow 内生效，出不去 */
    .btn { color: red; }
  </style>
  <div class="subapp-root">子应用内容</div>
`;
浏览器原生保证了边界，不需要自己做选择器前缀或运行时劫持。

2. 在微前端（qiankun / wujie / micro-app）里怎么用
qiankun：开启 sandbox: { strictStyleIsolation: true } 时，会把子应用的容器变成 shadow host，把解析出来的 HTML + 样式都塞进 shadow root。实验性 isolation 则是给选择器加属性前缀（不真正用 Shadow）。
wujie：默认用 Shadow DOM 做 CSS/DOM 容器，再配合 iframe 做 JS 沙箱，隔离更强。
micro-app：也支持 Shadow DOM 或自研类 Shadow。
带来的好处：CSS 污染基本解决，子应用怎么写样式都不用怕影响主应用或其他子应用。

最常见的坑（面试必问）：

弹窗 / Modal / Drawer / Tooltip / Dropdown 等第三方组件默认 appendTo: body，会逃出 shadow 边界 → 样式丢失、定位错乱、层级问题。
解决方法（项目里真实用的）：
把弹窗挂载点改到主应用的 body（Ant Design 的 getPopupContainer、Element 的 append-to-body 配置）。
或者关闭 strict Shadow，改用 experimental 前缀模式。
或者主应用提供统一的弹窗容器。
其他小坑：字体图标、全局动画、某些 CSS 继承、事件冒泡 retarget（事件 target 会变成 host）等，需要额外处理。

面试官：Shadow DOM 是如何做到隔离的？你们项目里怎么用的？有遇到什么问题吗？

它实现隔离的核心是浏览器在 shadow 边界上做了天然限制：内部的 CSS 不会泄漏到外部，外部的全局样式默认也进不来，DOM 查询默认也跨不过这个边界。只有 CSS 变量、::part、::slotted 这些明确设计的通道才能穿透。模式上我们一般用 open，方便主应用必要时访问。
