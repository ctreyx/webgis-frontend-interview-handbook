

面试官：qiankun 里主子应用状态通信是怎么做的？和 iframe 的 postMessage 比有什么区别？

我：qiankun 的通信比 iframe 的 postMessage 方便很多。iframe 因为物理隔离，基本只能靠 postMessage，需要自己定义消息协议、做 origin 校验、处理异步，比较繁琐。qiankun 同页 + 沙箱，官方主要提供两种方式。

第一种是 **props**：主应用在 registerMicroApps 时传入 props，子应用在 mount(props) 里直接接收。可以传数据、函数、回调，非常灵活，适合下发登录信息、权限、配置、工具方法等。我们项目里（天府科技三态）就是用 props 把用户信息和权限传给运行态、运维态。

第二种是官方的 **initGlobalState**：主应用调用 initGlobalState 初始化一个全局状态，返回 actions（setGlobalState、onGlobalStateChange、offGlobalStateChange）。子应用通过 props 拿到这些方法，可以监听和修改。它内部是发布-订阅模式，set 的时候浅合并并通知所有监听者。适合简单的全局状态，比如主题切换、语言、简单通知。

但 initGlobalState 只适合少量、一级的简单字段，大数据或复杂对象不推荐，有性能和冲突风险。实际项目中我们会结合自定义 EventBus 或 props 传回调函数来做更复杂的通信，保证主应用作为稳定基座，子应用既能独立运行又能协作。

整体通信协议我们会文档化，配合独立部署，这样多团队并行时不会乱，也符合架构上“项目结束留下可复用资产”的目标。

# 其他通讯
面试官：除了 props 和 initGlobalState，qiankun 还有其他主流的通信/传信息方式吗？

我：有的。官方主要就 props 和 initGlobalState 两种，但实际项目中我们还会用几种更灵活的补充方式，基本能覆盖所有场景。

最主流的三种补充是：

回调函数 / 方法下发（最常用）：
在 props 里直接传函数，比如 onRefresh、getToken、updateUser。子应用调用这些函数就能反向通知主应用或获取最新数据。简单、类型安全，我们天府项目里权限刷新、数据同步很多都用这个。

全局 EventBus（自定义事件总线）：
主应用创建一个 EventBus（用 mitt 或 eventemitter3），通过 props 下发给所有子应用。子应用之间、主子之间都可以 $emit / $on。适合中等复杂度的事件通知，比如“关闭新手导航”“全局 loading”“跨应用刷新列表”。比 initGlobalState 更自由，不受一级字段限制。

共享状态模块 / Store 实例：
把 Redux、Pinia、Vuex 的 store 实例通过 props 传下去，或者结合 monorepo/Module Federation 做成共享模块。适合复杂业务状态。同技术栈时体验最好。

另外还有一些场景化的：

路由 query/params 传简单标识；
自定义 CustomEvent（注意沙箱兼容）；
实在强隔离时退回 postMessage；
极复杂实时数据走 WebSocket 后端中转。
选型原则我一般是：

初始化数据和权限 → props
简单全局状态 → initGlobalState
事件通知 → EventBus + 回调
复杂状态 → 共享 Store
保持主应用作为稳定基座，通信协议文档化，这样既支持独立交付，又不会让子应用之间耦合太死。我们天府三态项目基本就是这套组合拳。


### 1. qiankun 状态/通信完整原理（先学透）

qiankun 通信主要有 **官方两种 + 自定义补充**：

**① props（最常用、最推荐做初始化）**
- 主应用在 `registerMicroApps` 时传 `props`，或在生命周期钩子里动态传。
- 子应用在 `mount(props)` 里直接接收。
- 特点：简单直接、支持传任意数据（对象、函数、回调、实例）。
- 单向为主（主 → 子），也可传函数让子应用回调主应用（实现反向）。
- 适合：登录信息、权限、用户数据、配置、工具函数、全局 EventBus 实例等。
- 子应用独立运行时 props 为空，需要做兼容。

**② initGlobalState（官方全局状态，发布-订阅）**
- 主应用：
  ```js
  import { initGlobalState } from 'qiankun';
  const actions = initGlobalState({ user: null, theme: 'light', token: '' }); // 初始化
  actions.onGlobalStateChange((state, prev) => { /* 监听 */ });
  actions.setGlobalState({ theme: 'dark' }); // 修改（浅合并，只改已存在的一级属性）
  ```
- 子应用：通过 `props` 拿到 `onGlobalStateChange` / `setGlobalState` / `offGlobalStateChange`（qiankun 会自动注入），用法一样。
- **原理**（源码级）：
  - 内部维护一个全局 `globalState` 对象 + `deps` 观察者列表（id → callback）。
  - `setGlobalState`：浅检查变化 → cloneDeep 更新 → `emitGlobal` 遍历所有 deps 触发回调（传新 state 和 prev）。
  - `onGlobalStateChange`：注册/覆盖当前应用的 callback（每个应用通常一个）。
  - `offGlobalStateChange`：卸载时自动清理。
  - 本质是简单的 **发布-订阅（Observer）** + 浅合并，不是完整的 Redux/Vuex。
- 限制（你说的“少量字段”）：
  - 只建议一级简单属性。
  - 子应用只能改初始化时已有的一级 key（安全限制）。
  - 不适合大数据、嵌套深对象、高频更新（有 cloneDeep 开销）。
  - qiankun 3.x 已提示将移除，建议逐步用更好方案。

**③ 自定义/补充方式（项目中真实会用）**
- 主应用提供全局 EventBus / 自定义事件（window 或 props 下发）。
- 传函数/回调：props 里传 `onRefresh`、`getToken` 等。
- 共享模块（结合 Module Federation 或 monorepo 公共包）。
- 浏览器 storage + 事件（不推荐，有隔离问题）。
- 如果子应用是强隔离（iframe 模式），才退回 postMessage。
- RxJS、共享 store 实例等（需处理好沙箱）。

**对比 iframe**：
- iframe：物理隔离，只能 postMessage（字符串化、异步、协议自定、安全校验），体验差、代码多。
- qiankun：同页运行 + 沙箱，props 和全局状态更自然、同步性更好、支持传函数，开发体验远强于 iframe。

**架构建议**（结合岗位）：
- 初始化数据、权限、用户 → props。
- 简单跨应用通知（主题、语言、全局 loading、消息提示）→ initGlobalState。
- 复杂业务状态 → 公共状态库 或 主应用中台服务 + 回调。
- 始终保持主应用是“稳定基座”，通信协议要版本化、文档化，方便独立交付和后续维护。
