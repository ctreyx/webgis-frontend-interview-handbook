

面试官：简单聊一下微前端这些吧。

我：好的。微前端本质上就是把一个大的前端应用拆成多个独立的子应用，让不同团队可以并行开发、独立部署、技术栈也可以不一样，最后在主应用里组装起来。核心价值是提升交付效率和资产复用，特别适合中后台或多业务线的场景。

我实际用得比较多的是 qiankun。它基于 single-spa，主要做了三件事：
一是 HTML Entry，直接 fetch 子应用的 index.html，自动解析里面的 JS、CSS，不用子应用改造成 JS Entry；
二是沙箱隔离，默认 ProxySandbox，给每个子应用一个假的 window，读写都代理过去，多实例互不影响，还有 Snapshot 和 Legacy 做降级；
三是生命周期和路由劫持，子应用导出 bootstrap、mount、unmount，主应用根据 activeRule 自动挂载卸载。通信用 props 下发登录信息，或者 initGlobalState 做全局状态。

样式上支持 Shadow DOM 严格隔离，弹窗定位问题我们一般把 Modal 挂到主应用 body，或者用实验性 scoped。公共依赖通过 externals 抽出去，主应用统一提供，子应用体积小很多。

除了 qiankun，我还对比过其他主流方案：

iframe 隔离最强、零改造，但性能和体验差，只适合第三方或高安全场景；
single-spa 是底层编排器，只负责路由和生命周期，沙箱得自己做，qiankun 就是在它基础上产品化的；
Module Federation 是 Webpack5 的模块联邦，通过 remoteEntry 共享模块，性能最好、依赖单例，但更适合同技术栈，隔离靠约定；
wujie 用 iframe 跑 JS + Shadow DOM 跑样式，再用 Proxy 桥接，隔离几乎物理级，子应用基本零改造，保活和多开很强；
micro-app 则是自定义元素的方式，用起来像普通组件，接入成本最低，也是 HTML Entry + Proxy 沙箱。


# 每个优缺点
“当项目存在多个技术栈，或者希望把不同团队/不同时期的项目拼接在一起时，微前端有几种主流选型，我一般从隔离性、性能、接入成本、技术栈兼容、适用场景这几个维度来对比。

iframe：接入最简单，隔离性最强（原生多文档），任意技术栈。但性能差、白屏、弹窗只能在 iframe 内部（无法真正居中到视口）、路由历史不同步、通信只能靠 postMessage，url 传参还容易暴露信息。只适合第三方或高安全临时嵌入。

single-spa：纯路由 + 生命周期编排层，非常轻，但没有任何沙箱和 HTML Entry，接入成本高，需要自己实现隔离。

qiankun：在 single-spa 基础上加了 HTML Entry、Proxy/Snapshot 沙箱和样式隔离，开箱即用。主应用注册 name、entry、container、activeRule，路由变化时 fetch 子应用 HTML 解析加载，支持完整生命周期。隔离性较好，适合多技术栈和遗留系统，社区最成熟。缺点是弹窗在 Shadow DOM 下会样式丢失，需要手动挂到主应用 body。

wujie（腾讯）：iframe 跑 JS + Shadow DOM 跑样式，再用 Proxy 桥接，隔离性几乎最强，子应用零改造，保活和多开很优秀。通信有 EventBus，但相对繁琐一点；有一定 iframe 开销，不过可预加载缓解。

micro-app（京东）：基于 WebComponent 自定义元素，用起来像普通组件，HTML Entry + Proxy 沙箱，接入成本极低，适合快速渐进式落地。

Module Federation：Webpack5/Rspack 的模块联邦，通过 remoteEntry 共享模块，性能最好、依赖可单例。最适合同技术栈，配置和版本协商有成本，隔离靠约定。

我们最终选 qiankun 的原因：天府科技项目有开发态、运行态、运维态，低代码部分是 React，其他是 Vue，多技术栈 + 需要稳定嵌套预览，2022 年 qiankun 成熟度最高、资料最多、对遗留系统友好。主应用做 shell + 权限 + 公共组件，子应用独立仓库独立部署，完美支撑并行交付。

什么情况下会切换：

强隔离 + 零改造 + 保活 → wujie
同技术栈追求极致性能和模块复用 → Module Federation
想最快接入、像组件一样用 → micro-app
纯第三方 → iframe
从架构角度看，不管选哪个，主应用都要做成稳定基座，子应用独立演进，配合 monorepo 沉淀组件，才能真正实现项目结束 = 团队资产开始，复用率明显提升。”
