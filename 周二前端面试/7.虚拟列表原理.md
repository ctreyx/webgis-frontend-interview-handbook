# 虚拟列表真正用到的浏览器 API / 特性（面试重点）


通过 start / end 计算只渲染可视区 + 上下缓冲（overscan，比如多 5-10 条），用 JS 计算换取更少的 DOM，避免大量 DOM 造成的回流/重绘/内存问题。


# 总结给面试官的一句话：
“虚拟列表没有专门的浏览器 API，核心是监听 scroll 拿到 scrollTop，结合容器高度和 item 高度算出 start/end（加 overscan），只渲染这部分 DOM，用占位元素撑滚动条，用 transform 定位。辅助会用到 ResizeObserver、requestAnimationFrame，有些实现结合 IntersectionObserver，新浏览器还可以用 content-visibility 做轻量优化。”

完整面试口语回答（虚拟列表原理 + API，约 1 分 20 秒 – 1 分 40 秒）
“虚拟列表的核心思想是只渲染可视区域内的列表项，加上上下一点缓冲（overscan），用 JS 计算换取更少的 DOM 数量，从而大幅降低内存和渲染压力。

具体实现：
监听容器的 scroll 事件，拿到 scrollTop 和容器 clientHeight。
如果是固定高度，直接 startIndex = Math.floor(scrollTop / itemHeight)，endIndex = start + visibleCount + overscan。
动态高度就需要提前测量或缓存每项高度，用前缀和快速定位。

然后只渲染 start 到 end 的数据。
用一个占位 div 把总高度撑起来（总高度 = 数据量 × 平均高度），保证滚动条正常。
可见列表通过 transform: translateY(start * itemHeight) 定位到正确位置。

上下多渲染 5-10 条是为了快速滚动时不白屏。

用到的主要浏览器 API 就是 scroll 事件 + scrollTop + clientHeight + getBoundingClientRect（测高），优化会加 requestAnimationFrame 节流、ResizeObserver 监听容器变化。
有些实现会用 IntersectionObserver 来做可见性检测。
比较新的 CSS content-visibility: auto 可以让浏览器自己跳过离屏渲染，作为轻量补充，但真正万级以上数据还是得 JS 虚拟列表。

计算如果特别复杂，可以考虑放到 Web Worker，并做好高度缓存。
这就是用空间换时间、用计算换 DOM 的典型优化。”



具体用到的 API 主要是这些：

最核心、最常用：

scroll 事件（监听滚动）
element.scrollTop（当前滚动位置）
element.clientHeight / offsetHeight（可视容器高度）
列表项高度（固定高度直接用，动态高度用 getBoundingClientRect() 或缓存测量）
定位与撑开滚动条：

创建一个占位元素（phantom）高度 = 总数据量 × 每项高度，撑起真实滚动条。
可见列表用 transform: translateY(offset) 或 position: absolute + top 定位到正确位置（推荐 transform，减少回流）。
性能优化常用：

requestAnimationFrame：滚动时节流计算和渲染，避免卡顿。
ResizeObserver：监听容器大小变化，重新计算可见范围。
IntersectionObserver：部分高级实现会用它来检测元素进出可视区（或做无限滚动的 sentinel），比纯 scroll 更高效（异步、不卡主线程），但经典虚拟列表（react-window、vue-virtual-scroller、el-table-v2）主要还是 scroll + 计算。
较新的原生辅助（可以提加分）：

CSS content-visibility: auto + contain-intrinsic-size：浏览器自己跳过离屏内容的渲染（layout/paint），DOM 节点还在，实现超简单，适合中等长度列表。但它不是真正的虚拟列表（DOM 数量没减少，只是渲染跳过），万级以上数据还是得上 JS 虚拟列表。

进阶（你提到的）：

Web Worker：把复杂的动态高度预测/计算放到 Worker，避免主线程卡顿（可选，大多数库不用）。
缓存：高度缓存、已渲染项复用（对象池）。
