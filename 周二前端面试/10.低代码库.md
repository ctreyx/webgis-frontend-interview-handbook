# 你们的组件库是如何用 monorepo 管理的？
# 如何做版本管理、发布，以及处理 Breaking Change？
# 如何保证组件质量和文档，让团队复用率真正达到 60% 左右？



我们组件库用 pnpm workspace monorepo 管理，主要解决多包共享依赖、统一规范、原子化提交和跨包引用方便的问题，最终支撑业务 60% 以上的复用率。

技术选型：workspace 管 packages（utils、hooks、atomic 基础组件、biz-general 业务通用组件如 SearchTable/ProTable、主题等）。打包选 Rollup，因为它 tree-shaking 更细粒度，产物更干净，没有 Webpack 那些额外 runtime 或冗余代码，对组件库这种‘按需导出’场景更合适。共享 ESLint、TSConfig、Vite 配置，保证风格和类型一致。

版本与发布：我们采用统一发布策略，而不是个人随时发。一般固定周四，发布前群里同步‘还有没有要合的改动’，确认后一起打。每次发布整体升一个小版本（比如 0.0.0 → 0.0.1），并维护详细 changelog：谁改的、什么时间、改了哪些组件/修复了什么。这样完全可溯源，出问题能快速定位到人和变更。版本统一能避免‘我本地是 0.0.3、你是 0.0.5’的混乱，对交付项目特别友好。

Breaking Change 处理：我实际还没碰到必须 break 的大改，但流程是明确的。先团队开会评估：能不能在原组件用 props/slots 扩展？成本和收益如何？如果一定要改现有 API，就先拉清单（哪些项目/页面在用），评估影响面，再逐个升级代码并回归。更推荐的做法是直接新写一个组件，而不是无限 if-else 扩展通用组件——否则后面就变成屎山，可读性和维护性都崩。比如去年军区项目，时间轴的样式和交互逻辑跟公司通用版完全不一样，我就单独抽象了一个，既不影响其他项目，又保证了通用资产的纯净。这其实就是在保护 60% 复用的长期价值。

质量与文档保障：每次更新强制记录更新人、时间、内容。早期靠 Code Review 推动大家用公司组件，现在升级成 AI + CI/CD 流水线：提交时 AI 做语义检查（是不是又重复造轮子、有没有违反分层、props 设计是否合理），再加上 lint、type-check、单测、构建。文档用 VitePress + Storybook，每个组件有 demo、API 表格、最佳实践，降低使用成本。新页面很多时候 80% 靠配置 SearchTable 这些就能出，真正做到资产化。

总结一下：monorepo + 统一规范发布 + 严格 BC 管控 + AI 质量门禁，让组件库从‘能用’变成‘愿意用、不敢乱造’，直接支撑架构层面的高复用和交付效率。项目结束后这些包还能沉淀到下一个项目，形成团队资产。”
