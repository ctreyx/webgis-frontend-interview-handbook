# WebSocket vs SSE —— 选型分析

┌──────────────┬────────────────────────┬────────────────────────┐
│ 维度 │ WebSocket │ SSE │
├──────────────┼────────────────────────┼────────────────────────┤
│ 通信方向 │ 全双工（双向） │ 单向（服务端→客户端） │
│ 底层协议 │ 独立协议 ws:// │ 基于 HTTP/1.1 │
│ 数据格式 │ 文本 + 二进制 │ 仅文本（text/event) │
│ 断线重连 │ 需手动实现 │ 浏览器自动重连 │
│ 连接数限制 │ 无 HTTP 并发限制 │ HTTP/1.1 下 6个/域名 │
│ 代理穿透 │ 部分代理不支持 │ HTTP 天然兼容 │
│ 浏览器支持 │ IE10+ │ IE 完全不支持 │
└──────────────┴────────────────────────┴────────────────────────┘

# // ❌ SSE 不适合的原因：

# // 1. 天气数据包含大量二进制数据（雷达图、风场网格）,用SSE只支持文本，必须base64编码，体积膨胀

// SSE 只支持文本，二进制必须 Base64 编码 → 体积膨胀 33%
const radarData = new Float32Array(512 \* 512); // 1MB 的雷达网格
// SSE: 必须 btoa() → 1.33MB + 编解码开销
// WS: 直接发送 ArrayBuffer → 1MB，零额外开销

# // 2. 天气项目需要双向通信 ，SSE只能单项，无法做到通知后台

// 用户在地图上框选区域 → 告诉服务端"我只要这个区域的数据"
// 用户切换图层（温度→降水）→ 需要通知服务端切换推送内容
// SSE 做不到，必须另开 HTTP 请求，两条通道维护成本高

# // 3. 高频推送场景

// 雷达数据 6分钟/帧，台风路径实时更新，预警信息秒级推送
// SSE 在 HTTP/1.1 下有 6 连接限制，多图层同时推送会阻塞

# 总结：SSE 适合"新闻推送"这类纯文本、单向、低频场景；天气项目涉及二进制传输 + 双向通信 + 高频多通道，WebSocket 是唯一合理选择。
