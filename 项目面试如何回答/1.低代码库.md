

1. 核心痛点 进入公司后发现前端严重不规范：

单个页面经常上千行，逻辑、视图、地图交互全揉在一起；新项目大量复制粘贴老项目代码，导致相同功能在多个项目里存在3-5个版本，维护成本极高，新人上手一个中等页面至少要1-2天。公共能力完全没有沉淀成公司资产，每个项目都在重复造轮子。

2. 目标与选型决策 我定的目标不是“做一个组件库”，而是把重复问题变成可复用的团队资产，同时兼顾新项目快速启动和老项目渐进迁移。

技术选型：

采用 pnpm workspace  的 monorepo 管理（当时也对比过Nx，最终选Turborepo是因为构建缓存和任务编排更轻量，团队学习成本低）。

打包用 Rollup（配合 @rollup/plugin-typescript、terser 等），输出三种格式：ESM（现代项目主用）、CJS（兼容老项目）、UMD（偶发CDN场景）。选择Rollup而不是纯Vite Library Mode，是因为当时需要对打包产物做更精细的控制（外部依赖排除、多入口、类型文件精准生成），Tree-shaking效果也更稳定。

前期我花了两周梳理全公司项目，识别出约50个高频可复用点，最终通过「扩展性、复用度、抽离难度、业务通用性」四个维度评分，选出30个核心组件进入组件库（基础组件 + 业务组件 + 地图相关组件）。

 
4. 接入标准、版本管理与落地策略

先在新项目强制使用，形成“封装 → 使用 → 发现问题 → 组件库迭代发布”的正向闭环。
老项目采用渐进迁移，不搞一刀切。通过 Code Review 卡点，新增页面必须优先用组件库。

5. 量化结果（更严谨的口径）

复用率：新项目中，UI和业务组件层面约60%直接来自组件库（通过统计 import 次数和代码行占比得出），重复代码量明显下降。
启动效率：早期新项目从零到可演示页面平均5天左右（大量复制+修改），现在核心页面3天内能跑起来，提升约40%。
额外收益：新人上手公共部分时间缩短一半以上；地图相关页面的维护成本下降最明显。
组件库目前在公司内部多个项目线稳定运行，并沉淀了设计规范、接入文档和Meta描述标准。

6. 我的角色与思考 我作为架构负责人，从0到1完成了技术选型、monorepo搭建、核心组件抽离、Meta描述规范制定，以及第一版文档。核心基础设施代码我亲自写，然后把组件实现通过Meta json详细描述后交给团队成员开发，我做Code Review和最终把关。
