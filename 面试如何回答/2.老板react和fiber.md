 
# ✅ 第一点：Fiber 解决了什么问题

React 15 的 Stack Reconciler 是递归遍历虚拟 DOM 树，调用栈很深，同步且不可中断。一旦组件树很大，主线程长时间被占用，用户的输入、动画等高优先级任务就得不到响应，造成卡顿。

Fiber 架构把递归变成了链表遍历（每个 Fiber 节点有 child、sibling、return 三个指针），这样遍历过程可以随时暂停、恢复，每处理完一个 Fiber 节点就可以检查是否需要让出主线程。

💡 关键词你要记住：从递归变成链表迭代，这才是 Fiber 可中断的数据结构基础。




# c✅ 第二点：MessageChannel 替代 requestIdleCallback


原因	说明
兼容性差	很多浏览器不支持，Safari 到目前也不完全支持
触发频率太低	rIC 在浏览器真正空闲时才触发，一般只有 20fps（50ms 一次），远达不到流畅渲染的要求
不可控	浏览器对"空闲"的判断不可预测，React 需要自己掌控调度节奏
所以 React 的做法是：

用 MessageChannel 的 port.postMessage() 触发一个宏任务，在这个宏任务里执行工作，同时用 performance.now() 手动计算时间，默认每次工作 5ms，超时就通过 shouldYield() 让出主线程，等下一个宏任务再继续。

💡 核心一句话：React 没有用浏览器的空闲检测，而是自己实现了一个 5ms 时间切片的调度器（Scheduler）

宏任务 vs 微任务 时序对比：

宏任务（MessageChannel）✅
[React任务5ms] → [浏览器渲染] → [React任务5ms] → [浏览器渲染]
↑ 每个宏任务之间浏览器都能渲染，用户感觉流畅

微任务（Promise）❌
[React任务] → [微任务继续] → [微任务继续] → 浏览器没机会渲染！
↑ 微任务队列清空才轮到渲染，等同于同步阻塞

setTimeout ⚠️
[React任务5ms] → [4ms空等] → [React任务5ms] → [4ms空等]
↑ 浪费 4ms，高频调度下帧率损失明显



# React 的 MessageChannel 触发的宏任务，执行 5ms 后通过 shouldYield() 让出主线程——让出之后，浏览器在这个空档里具体做了什么？React 是在哪个时机再次"抢回"主线程继续执行的？


微任务清空 → rAF → 样式计算 → 布局 → 绘制（这就是用户感知到的流畅） 

超过 5ms，React 停止工作，但在停止之前，它会再调用一次 port.postMessage()，提前把下一个宏任务塞进消息队列，浏览器渲染完了，从消息队列里取出下一个宏任务——就是刚才 React 提前塞进去的那个 MessageChannel 任务，React 继续从上次暂停的 Fiber 节点恢复工作。
