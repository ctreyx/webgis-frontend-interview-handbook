### 第一层：先说清楚项目定位（10 秒）

> **"我们低代码平台的组件库是 Monorepo 架构，pnpm workspace 管理多个子包。组件、工具、样式、国际化、指令都是独立的 package。最终通过统一入口打包发布到公司私有 npm 仓库，业务平台 npm install 安装使用。"**

---

### 第二层：说构建工具和流程（30 秒）

> **"构建工具链是 Gulp 做任务编排，Rollup 做打包，ts-morph 生成类型声明。整个构建流程大概是这样：**
>
> 先 clean 清空产物目录，然后并行执行四个任务：
> - **模块化构建**：Rollup 用 preserveModules 保留源码目录结构，分别输出 `es/` 目录的 ESM 格式和 `lib/` 目录的 CJS 格式
> - **完整打包**：Rollup 把入口打成 UMD 全量包，包括压缩版和非压缩版，还有语言包单独拆分
> - **类型生成**：用 ts-morph 解析 Vue SFC 的 script 部分生成 `.d.ts`，拷贝到 es 和 lib 目录
> - **主题样式**：编译输出全量 CSS"

---

### 第三层：说产物格式和用途（20 秒）

> **"最终产物是三种格式同时输出：**

```
┌──────────────────────────────────────────────────────┐
│                                                       │
│  es/*.mjs     → ESM 按需引入，支持 Tree Shaking     export { Button } from './Button'   │
│  lib/*.js     → CJS 兼容老项目和 Node 环境      module.exports = { Button }        │
│  dist/*.full.js → UMD 全量包，script 标签直接引入     │
│                                                       │
│  另外还有：                                           │
│  dist/index.css      → 全量样式                      │
│  dist/locale/*       → 国际化语言包，按需加载          │
│  各目录 .d.ts        → TypeScript 类型提示            │
│  metadata.json       → 组件元数据，给低代码平台用      │
│                                                       │
└──────────────────────────────────────────────────────┘
```

> **package.json 里 module 指向 ESM 入口，main 指向 CJS 入口，打包工具优先读 module 走 Tree Shaking。"**

---

### 第四层：说低代码平台怎么消费（20 秒）

> **"组件库发布到公司私有 npm 仓库后，低代码平台安装使用。平台拿到包里的 `metadata.json`，里面有每个组件的名称、props、事件、插槽等元数据，平台据此自动注册组件到拖拽面板。渲染时从 `es/` 按需引入组件，配合 `dist/index.css` 加载样式。**
>
> **这个 metadata.json 是低代码和组件库解耦的关键——平台没有源码，只能靠这份元数据知道组件长什么样、有哪些配置项。"**

---

### 第五层：说设计亮点（主动加分）

> **"这套构建方案有几个我觉得设计得比较好的地方：**
>
> **第一，es 和 lib 目录保留了源码目录结构，不是打成单文件。** 这样平台如果只用 20 个组件，打包工具只会引入这 20 个，不会把几百个组件全打进去，真正实现按需加载。
>
> **第二，Vue 和 Cesium 这些大依赖声明为 external，放在 peerDependencies。** 不打进包里，由平台侧自行安装，避免两份 Vue 实例导致响应式冲突。
>
> **第三，metadata.json 随包发布，打通了组件库到低代码平台的注册链路。** 新增组件只要在 metadata 里补上元数据，平台那边不需要改代码就能自动识别。"

 # 一个追问
你们组件库打包输出了哪些格式？

为什么要同时输出 ESM 和 CJS 两种格式？分别在什么场景下被使用？

 

---

## 补充完整答案

### ESM 格式（.esm.js）
```javascript
export { Button } from './Button'
```
| 用途 | 说明 |
|------|------|
| Vite / Rollup 消费 | 构建工具直接识别，支持 tree shaking |
| 按需引入 | 用什么打什么，不会全量引入 |
| 现代浏览器 | 支持原生 `<script type="module">` |

---

### CJS 格式（.cjs.js）
```javascript
module.exports = { Button }
```
| 用途 | 说明 |
|------|------|
| Node.js 环境 | SSR、Jest 测试默认用 CJS |
| Webpack 4 以下 | 不能直接处理 ESM |
| 老项目兼容 | `require()` 语法 |

---

###   UMD 格式

> 组件库通常还会输出 **UMD 格式**，用于：
> - 浏览器 `<script>` 标签直接引入
> - CDN 场景，比如 `unpkg.com/your-lib`
> - 不需要构建工具，直接用

---

### package.json 里怎么声明

```json
{
  "main": "dist/index.cjs.js",   // CJS 入口
  "module": "dist/index.esm.js", // ESM 入口（构建工具识别）
  "unpkg": "dist/index.umd.js",  // CDN 入口
  "exports": {
    ".": {
      "import": "./dist/index.esm.js",
      "require": "./dist/index.cjs.js"
    }
  }
}
```

> `exports` 字段是现代写法，优先级高于 `main` 和 `module`，Node 12+ 支持
