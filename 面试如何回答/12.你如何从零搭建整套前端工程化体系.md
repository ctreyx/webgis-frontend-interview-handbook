# 最后问你一个开放性的问题：如果让你去一家新公司，从零搭建整套前端工程化体系，你会按什么顺序推进？第一周做什么、第一个月做什么、三个月做什么？


# 第一周：先观察再动手
第一周我不会急着搭东西，而是先做三件事：

第一，读项目代码。了解现有项目的目录结构、技术栈、构建方式、部署方式、代码风格。每个团队都有自己的历史包袱和习惯，不了解就乱改会踩坑。

第二，梳理现有问题。和团队成员一对一聊，问他们开发中最痛的点是什么——是构建慢？是部署麻烦？是代码风格不统一？是经常线上出 bug？找到最痛的那个点，优先解决。

第三，搭建最小可用的 CI/CD。先不做复杂的，就两步：ESLint 检查 + 构建验证。代码 push 后自动跑，不通过就阻断。让团队先习惯"提交代码有自动检查"这件事。

第一周的产出：一份可运行的基础流水线 + 一份团队痛点清单。"

# 第一个月：补齐基础设施
基于第一周发现的痛点，按优先级逐步补齐：

第一，本地检查。配置 husky + lint-staged，commit 时自动跑 ESLint 和 Prettier。这样开发者在本地就能发现问题，不用等 CI 跑完才知道代码不合格。

第二，完善流水线。在 ESLint 基础上加入 TypeScript 类型校验、构建产物验证。

第三，建立 Code Review 机制。合并主分支必须经过至少一个人 Review，我在前期会重点看每一个 MR，通过 Review 的过程把编码规范传递给团队。

第四，输出第一版开发规范文档。包括目录结构规范、命名规范、组件拆分原则、Git 提交规范。不用写得很完美，先有一版能用的，后面持续迭代。

第一个月的产出：完整的 CI/CD 流水线 + Code Review 机制 + 第一版开发规范。"

# 三个月：从"能用"到"好用"
第一，加入 AI 代码审查。ESLint 只能查语法层面的问题，定时器没清除、事件监听没移除这些语义层面的问题需要 AI 补齐。先设为警告模式观察准确率，稳定后再考虑阻断模式。

第二，沉淀组件库或公共模块。一个月的开发过程中肯定发现了很多重复代码，把它们抽成公共组件或工具函数，开始建设公司级组件体系。

第三，建立质量复盘机制。每两周回顾一次：CI/CD 拦截了多少问题、Code Review 发现了什么共性问题、线上有没有出过 bug。用数据驱动持续优化流程。

第四，迭代规范文档。把这三个月踩过的坑、积累的案例补充进文档。案例贴到团队群里但去掉姓名，表现好的推荐优秀员工，用正向激励推动规范落地。

三个月的产出：AI 代码审查 + 公共组件库雏形 + 质量复盘机制 + 完善的规范文档。新人入职时拿到这些文档和工具，一周内就能按照团队标准开始写代码。
