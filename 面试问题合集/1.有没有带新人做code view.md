### 第一：新人 Onboarding 体系

> "新人入职，我不会让他自己摸索。我做了一套标准化的 Onboarding 流程：
>
> **第一周：环境搭建 + 项目熟悉。** 我写了一份 Onboarding 文档，从 Git 权限申请、开发环境搭建、项目目录结构说明、本地启动步骤，到核心业务模块的架构图，全部文档化。新人照着文档走，半天就能把项目跑起来，不需要到处问人。
>
> **第二周：认领一个小需求。** 我会提前准备 2-3 个标注了'新人友好'的任务，复杂度可控，但能接触到核心代码链路。新人做完之后走 Code Review，我会在 Review 中详细写 comment，不只是说'这里要改'，而是解释'为什么要这样做、团队的约定是什么'。
>
> **第三周开始：正式进入迭代。** 分配正常需求，但前两个迭代我会做他的 Code Reviewer，之后逐步交给团队其他成员交叉 Review。"

---

### 第二：Code Review 制度

> "Code Review 是我们团队的硬性流程，从来没停过。但随着团队成熟，我做了三个阶段的演进：
>
> **第一阶段：我主 Review。** 团队初期人少，所有 MR 都经过我。我会在 Review 中写详细的 comment，这本身就是培养新人的过程。一般一个新人经过 10-15 次 Review，代码风格和架构意识就能对齐了。
>
> **第二阶段：沉淀规则，工具替代人工。** 我把 Review 中反复出现的问题——比如命名不规范、类型定义缺失、组件拆分不合理——沉淀成了 ESLint 自定义规则和团队规范文档。工具能拦住的问题不再浪费人工 Review 时间。
>
> **第三阶段：交叉 Review + 我做二审。** 团队成熟后，推行成员之间互相 Review，普通需求一个人 approve 就能合入，核心模块或架构变更需要我二审。这样既保证质量，又不会因为我一个人成为瓶颈。
>
> 通过这套机制，我们 Review 中发现的问题从早期平均每个 MR 8-10 条 comment，降到了后期 2-3 条，说明团队整体代码质量在持续提升。"

---

### 第三：技术规范体系

> "我建了一套完整的技术规范，不是口头约定，而是工具强制执行：
>
> - **代码层面**：ESLint + Prettier + Stylelint + TypeScript strict，保存自动格式化，提交前 lint-staged 检查，不过直接拦住
> - **提交层面**：commitlint 规范 commit message，不规范的提交不上去
> - **CI 层面**：MR 触发自动化流水线——lint 检查、类型检查、单元测试、产物体积检查，任何一项不过都不能合入
> - **文档层面**：规范写成文档，每个规则附带'为什么'，新人看完就知道团队的标准是什么
>
> 核心理念是——**能让工具干的事绝不靠人自觉，能在提交前拦住的问题绝不留到 Code Review。** 这样 Code Review 才能聚焦在架构设计和业务逻辑上，而不是纠结缩进和命名。"

---

### 第四：技术分享 + 成长路径

> "除了日常 Review，我还做了两件事推动团队成长：
>
> **第一，双周技术分享。** 每两周一次，轮流分享，主题不限——可以是踩过的坑、学到的新技术、做过的性能优化。我自己也参与分享，不是只让别人讲。目的是建立团队的技术交流氛围，让每个人都能从别人的经验中学到东西。
>
> **第二，一对一成长沟通。** 每个季度和每个成员做一次一对一，聊他当前的技术瓶颈、想往哪个方向发展、下个季度的成长目标。比如有个同事对可视化感兴趣，我就在分配需求时有意识地把 Cesium 地图相关的任务给他，让他在实战中成长，而不是只做 CRUD。"

---

### 第五：架构层面的团队赋能

> "作为架构师，我认为最高效的'带团队'不是我去教每个人怎么写代码，而是**通过架构设计降低团队的开发门槛**：
>
> - **项目脚手架**：我做了一套标准化的项目模板，新项目基于模板生成，目录结构、配置、规范、CI 全部内置，新人不用从零搭建
> - **公共组件库**：团队统一的组件库，npm 安装直接用，避免重复造轮子
> - **封装复杂度**：比如 Cesium 地图初始化、SSE 流式通信、权限控制这些复杂逻辑，我封装成公共 hooks 或 SDK，团队成员调用简单的 API 就行，不需要理解底层细节
>
> 这样即使是刚来的新人，也能快速产出，因为复杂度被架构层吸收了。"
